## 1. capcut-mate architecture

**Stack**: Python ≥3.11,<3.14, FastAPI + Uvicorn, `uv` package manager. Entry point `main.py` creates `app = FastAPI(title="CapCut Mate API")`, mounts `v1_router` at `/openapi/capcut-mate/v1`, and runs on `0.0.0.0:30000` in dev (Docker `CMD ["uv","run","main.py","--workers","4"]` in prod — `main.py` never reads `--workers`, so multi-worker behavior is suspect given in-process singleton state, see §6).

**Middleware stack** (`src/middlewares/{prepare,response,trace_context}.py`): `PrepareMiddleware` → `ResponseMiddleware` → `TraceContextMiddleware`. `ResponseMiddleware` forces **every** response — success or business error — to **HTTP 200** with a `{code, message, ...data}` envelope; only `code == 0` means success. No CORS middleware. No global auth; only `gen_video` optionally checks an `apiKey` against the vendor's own external SaaS billing endpoint (`https://jcaigc.cn/openapi/v1/user/points`, `src/utils/points.py`) when `config.ENABLE_APIKEY=true`.

**API surface** (`src/router/v1.py`, 34 endpoints, all under `/v1`, all POST except `get_draft`/`gen_video_active_count` which are GET). Request/response models in `src/schemas/*.py`, implementations in `src/service/*.py` (one file per endpoint). Notable: most bulk payloads (`video_infos`, `caption_infos`, `keyframes_infos`, etc.) are **JSON-encoded strings nested inside the outer Pydantic model** (double JSON encoding) — clearly designed for LLM/no-code tool-calling clients (Coze/Dify-style), not typical typed REST consumers.

Key endpoints and services:
- `create_draft` (`src/service/create_draft.py`) — copies `template/default2/` skeleton, loads via `ScriptFile.load_template`, registers in in-process `DRAFT_CACHE`.
- `add_videos`/`add_audios`/`add_images` (`src/service/add_videos.py` 634 lines, `add_images.py` 650 lines) — download URLs, build `VideoMaterial`/`VideoSegment` (or Audio/Image) objects, optional speed ramping from `scene_timelines`, add to a new track.
- `add_captions` (`src/service/add_captions.py`, **1265 lines, the largest/most complex service**) — `TextSegment` + `TextStyle`/`TextBorder`/`TextShadow`, fuzzy font-name/alias resolution, keyword-highlight overlay or fully-partitioned style ranges, "花字" (stylized text) resolution via a **5539-line generated file** `src/service/text_effect_map_generated.py`, in/out/loop text animations.
- `add_effects`/`add_filters`/`add_masks`/`add_keyframes`/`add_sticker` — each resolves a Chinese-language catalog name/ID to a CapCut/Jianying resource and attaches it to a segment (`add_keyframes` notably converts the caller's absolute-µs offset to a 0..1 fraction of segment duration and back to relative µs — an intentional double conversion).
- `save_draft` — trivial, calls `script.save()` on the cached `ScriptFile`.
- `gen_video`/`gen_video_status`/`gen_video_active_count` — see below; this is full server-side Windows RPA rendering, not just draft-file generation.
- `easy_create_material` — one-shot convenience combining audio+video+image+text.

**`src/pyJianYingDraft/` — the core draft-format engine (the most reusable part)**. Apache-2.0, forked from Gary Guan's upstream `pyJianYingDraft`, modified 2026 by Hommy (per `NOTICE`). A CapCut/Jianying "draft" is a directory containing `draft_content.json` (primary edit-graph: `canvas_config`, `duration` in **microseconds**, `fps`, `materials` object with ~40 typed sub-arrays, `tracks`), a byte-identical `draft_info.json` compatibility shim, `draft_meta_info.json` (copied from template, later localized by `draft_downloader.py`), and `assets/{videos,images,audios}/`.

- **Time unit: microseconds throughout**, confirmed `time_util.py:6` `SEC = 1000000`. `Timerange(start, duration)` stores both as `int` µs. Used consistently for `duration`, every segment's `target_timerange`/`source_timerange`, every keyframe's `time_offset`, every animation's `start`/`duration`. This directly matches the target project's own microsecond-integer timebase requirement (§67 of the master prompt) — **capcut-mate's time convention is a natural fit, autocut's is not** (see §2).
- **Class model** (`script_file.py`, `track.py`, `segment.py`, `video_segment.py`, `audio_segment.py`, `text_segment.py`, `effect_segment.py`, `animation.py`, `keyframe.py`, `local_materials.py`): `ScriptFile` (document root: width/height/fps/duration, `ScriptMaterial` bucket, `tracks: Dict[str,Track]`); `Track`/`TrackType` (typed by segment kind + `render_index` layering + overlap validation, i.e. client-side placement validation happens in this library, not deferred to CapCut); `BaseSegment` → `MediaSegment` → `VisualSegment` → `VideoSegment`/`StickerSegment`/`AudioSegment`/`TextSegment`; `EffectSegment`/`FilterSegment` (extend `BaseSegment` directly). `ClipSettings` (alpha/flip/rotation/scale/transform — transform_x/y are in **half-canvas-width/height units**, not pixels, a frequent bug source). `VideoMaterial`/`AudioMaterial` probe local files via `pymediainfo` or accept caller-supplied metadata for remote-URL mode.
- **Animations/keyframes**: `Animation`/`VideoAnimation` (in/out/group, mutually exclusive group-vs-in/out)/`Text_animation` (in/out/loop). `Keyframe` — **linear interpolation only** (`curveType: "Line"` hardcoded, no bezier/ease). `KeyframeProperty` enum covers position/rotation/scale/alpha/saturation/contrast/brightness/volume. Materials (animations/effects/masks/filters/transitions) are auto-collected into the script-level `materials` bucket **only when the segment is added to a track via `ScriptFile.add_segment`** — constructing a segment and forgetting to add it silently drops its materials (a footgun).
- **`jianying_controller.py` — real Windows UI Automation (RPA), not file I/O.** Hard-fails to import on non-Windows. Drives the actual **Jianying Pro (China-region)** desktop app via Microsoft UI Automation COM APIs + `pyautogui`: finds the draft tile by name, clicks Export, sets resolution/fps via UIA control lookups, clicks a **hardcoded screen coordinate** (`pyautogui.click(x=996, y=597, ...)`, line 519) to dismiss a popup, polls for completion, moves the output file. Window matcher hardcodes `Name == "剪映专业版"` (Jianying Pro's Chinese name) — **not validated against international CapCut's window/control layout at all**. Extensive COM-transient-error retry logic (`is_com_uia_error`, matches specific HRESULTs and Chinese error substrings).
- **`template_mode.py`** — `ImportedTrack`/`ImportedSegment`/`EditableTrack` for surgically editing a pre-existing (non-library-created) draft, with configurable `ShrinkMode`/`ExtendMode` policies for material replacement. Present in the library but not exercised by the HTTP service layer's own `create_draft` flow, which always starts from the bundled skeleton template.

**`gen_video` rendering pipeline** (`src/service/gen_video.py`, `src/utils/video_task_manager.py`): confirmed this is **real automated rendering**, not just draft generation. `VideoGenTaskManager` singleton runs a 3-phase async pipeline per submitted draft: (1) download phase — fetches the draft into a **hardcoded Windows path** `config.py:43` `C:/Users/1/AppData/Local/JianyingPro/User Data/Projects/com.lveditor.draft`, verifies readiness, rejects drafts under 3s; (2) export phase — acquires a process-global lock (only one Jianying export at a time), calls `JianyingController().export_draft(...)`, retries known-flaky failure signatures, and on failure force-kills Jianying (`taskkill /F /T /IM JianyingPro.exe`) and purges stale draft directories; (3) upload phase — uploads the MP4 to cloud storage, deducts points, schedules deferred deletion. Status polling checks an in-memory dict first, falls back to a SQLite store (`src/utils/video_task_store.py`) for terminal results only.

**Storage/media utilities**: `src/utils/media.py` (ffprobe wrapper via `pymediainfo`), `src/utils/download.py` (900+ line hand-rolled resumable HTTP downloader), three interchangeable **China/APAC cloud object-storage backends** — Tencent COS (`cos.py`), Alibaba OSS (`oss.py`), Volcano/ByteDance TOS (`tos.py`) — selected by priority via `upload_file.py`, all issuing time-limited presigned URLs (no S3/R2/Backblaze option). `draft_cache.py` — in-process LRU (`DRAFT_CACHE`, cap 100) mapping `draft_id → ScriptFile`; **this is the primary edit-session state store**, meaning a draft is invisible across processes and evicted drafts become API-inaccessible even though the file persists on disk. `draft_lock_manager.py` — per-process `asyncio.Lock`-per-draft-id (not cross-process/distributed). `draft_cleanup.py`/`deferred_delete.py`/`jianying_export_cleanup.py` — background retention sweeps, the last of which force-kills Jianying and `shutil.rmtree`s stale draft directories on export failure.

**`desktop-client/`** — a separate, **MIT-licensed** (different author: "gogoshine", 2025) Electron app. Not a video editor and not a wrapper around the FastAPI editing endpoints — it's a purpose-built **draft-file downloader GUI**: fetches a draft manifest, classifies referenced files, downloads them via `nodeapi/resumableDownload.js` into the locally-detected Jianying/CapCut draft folder so the user can open the real desktop app. The one directly reusable piece is **`nodeapi/draftPathDetect.js`**'s path-detection heuristic: on Windows it builds `AppData\Local\JianyingPro\User Data\Projects\com.lveditor.draft` and searches the current user's home dir, then **every subdirectory of `C:\Users`**, confirming a match via presence of `root_meta_info.json` or `.recycle_bin`; on macOS it checks **both** `~/Movies/CapCut/...` and `~/Movies/JianyingPro/...` (international + China naming) — an asymmetry versus the Windows path list, which only ever probes `JianyingPro`, never `CapCut`. No registry lookups anywhere.

**Config data catalogs**: `config/huazi.json` (174KB, ~8,366 entries, stylized-text effect catalog, includes `is_vip` gating) and `config/sticker.json` (**62.5MB**, sticker catalog with ByteDance CDN URLs carrying **time-signed, expiring** query parameters — the catalog rots over time, nothing refreshes it). Both are unattributed exports of ByteDance-internal China-region catalogs.

**Docker**: `Dockerfile` (`python:3.11-slim`, `uv sync`, bundles a `tools/ffprobe` binary, `EXPOSE 30000`, runs as root). `docker-compose.yaml`/`docker-compose.example.yaml` run **only the Linux-containerizable half** (FastAPI draft-generation API + nginx) — no cloud-storage credentials, no `ENABLE_APIKEY`. The RPA/render half (`gen_video`) necessarily runs as a **separate, non-containerized process on a real Windows host** with Jianying Pro pre-installed and logged in — two physically distinct deployment targets share one codebase.

**Tests**: 76 files under `tests/`, real `pytest`-discovered suites (`test_*.py`, some `pytest.mark.asyncio`) plus **6 `manual_test_*.py` files that pytest's default discovery never picks up** (one, `manual_test_video_infos.py`, re-implements its own copy of the function it claims to test rather than importing production code — dead-weight/drifted coverage). Heaviest coverage: captions/text (fonts, keyword highlighting, animation), keyframes, video duration handling, draft locking/concurrency, storage upload. No visible dedicated tests for `add_effects`, `add_filters`, `add_text_style`, `easy_create_material`, or COS/OSS/TOS provider-selection order.

**Existing limitations** (see also §6 Technical Risks): RPA-based rendering is coordinate/UIA-selector-brittle and validated only against China-region Jianying Pro, not international CapCut; hardcoded per-deployment paths and draft IDs in source; in-process-only singleton state incompatible with the `--workers 4` the Dockerfile requests; hard external billing-SaaS dependency in `gen_video`; triplicated resumable-download logic across three files; string-encoded nested JSON API shape; HTTP status codes are meaningless (always 200).

## 2. autocut architecture

**Stack**: Tauri 2 + Rust (edition 2021, rust-version 1.77) + Svelte 5 (runes) + TypeScript (strict), built with Vite 6, pnpm. Bundle identifier `dev.cobanov.autocut`. Rust dependency surface is small and focused: `tauri`, `tauri-plugin-{dialog,notification,shell}`, `serde`/`serde_json`, `anyhow`, and **`voice_activity_detector = "0.2"`** (wraps ONNX Runtime running a **Silero V5** VAD model — confirmed via `Cargo.lock`'s `ort`/`ort-sys` transitive deps and in-code comments).

**App assembly** (`src-tauri/src/lib.rs`): `tauri::Builder` registers the three plugins, `.manage(AppState::default())`, and `invoke_handler!` for 11 commands. `AppState` holds three single-slot cancellation flags (`export_cancel`, `detect_cancel`, `waveform_cancel`, each `Mutex<Option<Arc<AtomicBool>>>`) plus an `AnalysisCache` — **only one export/detect/waveform job is supported concurrently, globally**, appropriate for AutoCut's one-project-at-a-time UX but not for a multi-project editor.

**Rust modules** (`src-tauri/src/`):
- **`commands.rs`** — the full IPC surface: `open_video`, `open_track`, `compute_waveform`, `detect_silence`, `export_mp4`, `export_fcpxml`, `cancel_export`/`cancel_detect`/`cancel_waveform`, `diagnostic_info`, `reveal_in_finder`. `AnalysisCache` is a single-slot cache (keyed by canonicalized path+mtime+len) holding decoded PCM (`Arc<Vec<i16>>`) and per-chunk VAD scores (`Arc<Vec<f32>>>`) — this is what makes re-detecting after a slider change "free" (only re-segmentation reruns, not the expensive ffmpeg decode + model inference).
- **`probe.rs`** — shells `ffprobe -show_streams -show_format`, parses to `MediaInfo {path, duration, fps, width, height, has_video, has_audio, start_timecode}`. Handles `avg_frame_rate` `0/1`/`0/0` fallback to `r_frame_rate`.
- **`audio.rs`** — `ffmpeg -vn -ac 1 -ar 16000 -f s16le` piped to memory incrementally as raw `i16` (not `f32` up front, halves peak memory: ~115MB vs ~690MB for a 2-hour source).
- **`vad.rs`** — **the core ML integration**. `CHUNK_SIZE = 512` samples (32ms @ 16kHz, Silero V5's fixed window). Two-phase, deliberately split for caching: `score_chunks()` (expensive, ~112k model calls/hour of audio) then `segments_from_scores()` (cheap, pure post-processing: threshold + hysteresis [release threshold = threshold−0.15, floor 0.05] → merge-close → drop-short). `VadParams {threshold, min_silence_ms, min_speech_ms}` defaults `0.5/100/150` match the README's slider table exactly. Output `SpeechSegment {start, end}` in **seconds (f64)** — no confidence field retained beyond the raw probability consumed during segmentation. 15 inline unit tests.
- **`cutlist.rs`** — the "cut algebra". `CutKind::{Keep,Remove}`, `Cut{start,end,kind}`, `CutList{source_duration, intervals}` — always tiles `[0, source_duration]` exactly, alternating. `CutList::from_speech_segments(segments, duration, pad)`: pad each side, clamp, merge overlaps, walk left-to-right emitting Remove/Keep. All `f64` seconds; **no rounding/frame-snapping** at this layer (that happens only in `timecode.rs` at FCPXML-render time). Rust never sees "manual edit" as a concept — that's entirely a frontend concern (`src/lib/cuts.ts`).
- **`timecode.rs`** — **internal representation is `f64` seconds throughout**, not integer microseconds. `TimecodeRate{nominal_fps, is_drop_frame, frame_duration_num/den}` (rational, used only for FCPXML rendering and SMPTE parsing) with NTSC-rate detection and an explicit degenerate-fps guard (regression-tested after a real bug produced a ~4.8-million-year "frame"). **This is the single biggest timebase-compatibility gap versus the target project's mandated integer-microsecond internal clock** — every module, test fixture, and serde field here assumes float seconds; reuse requires a conversion layer at the boundary, not a drop-in.
- **`sync.rs`** — **misleadingly named**: it is only a 20-line mutex-poisoning-recovery helper, *not* the multi-track alignment logic. The actual alignment lives in `commands::open_track` (computes `offset = parse_smpte(track_tc) - parse_smpte(reference_tc)` when both sides carry embedded timecode) and in `export_fcpxml.rs`'s per-keep track-intersection logic.
- **`export_mp4.rs`** — builds an ffconcat list (`file '<source>'` + `inpoint`/`outpoint` per kept interval) and invokes `ffmpeg -f concat -safe 0 ... -c:v libx264 -preset veryfast -crf <N> [-vf scale] [-c:a aac | -an]`. Chosen over `filter_complex select` because the filtergraph approach fails to allocate past a few hundred intervals. **Always re-encodes** (no lossless/smart-cut path, explicitly deferred by upstream). **No hardware acceleration** (no NVENC/QSV/AMF anywhere). Progress via `-progress pipe:2` parsing. Cancellation deletes the partial output on failure.
- **`export_fcpxml.rs`** — emits FCPXML 1.11 targeted at DaVinci Resolve/Premiere relink behavior. `Track{path, name, duration, start_timecode, has_video, has_audio, offset}` is the actual multi-track data model (not `sync.rs`). Lane assignment fans video up / audio down from the primary storyline. Per-keep-interval, intersects each linked track's `[offset, offset+duration]` window against the keep range to decide whether/how much of that track contributes as a nested connected-clip. 12 tests cover drop-frame rationals, lane stacking, tracks that stop early/start late/partially cover a keep.
- **`waveform.rs`** — simple peak-per-bin downsampler, no timestamps embedded (frontend derives bin↔time mapping externally).
- **`binaries.rs`** — sidecar resolution with a `#[cfg]` compile-time `TARGET_TRIPLE` matrix explicitly covering **Windows x86_64 both MSVC and GNU ABI** (no ARM64 Windows). `build.rs` fetches ffmpeg/ffprobe: Windows/Linux from a **pinned, SHA-256-verified** BtbN GitHub release (manually rotated periodically — documented incident where a stale pin "died" after ~2 weeks of BtbN pruning daily builds); macOS from unpinned, **unverified** endpoints. `AUTOCUT_STUB_SIDECARS=1` lets `cargo test --lib` run on a fresh checkout without the ~200MB fetch.

**Frontend** (`src/`): `App.svelte` (topbar + Dropzone-or-workspace layout via nested `ResizableSplit`). `lib/types.ts` **manually mirrors** the Rust structs field-for-field ("Keep in sync" comment, no codegen/schema validation — a maintenance risk at the current small IPC surface that will compound as the new project's surface grows). `lib/api.ts` — one typed `invoke()` wrapper per command. `lib/cuts.ts`/`cuts.test.ts` — a **distinct, complementary** layer (not a duplicate of Rust's `cutlist.rs`): manual keep-interval editing (`clampKeepEdge`, `normalizeKeeps`, `tileCutList`, `resolveForExport`), playback pre-emption (`skipTargetFor`), transport navigation — 41 vitest tests. `lib/store.svelte.ts` — single `EditorStore` class using Svelte 5 `$state` runes directly as class fields, with a monotonic `sessionId` race-guard so stale async responses from an abandoned video load can never clobber current state. Components: `Dropzone`, `ExportPanel` (quality/resolution, linked-track list, progress), `ManualCutPanel` (cut list editor), `ParameterPanel` (the four detection sliders), `ResizableSplit` (generic, `localStorage`-persisted), `Slider`, `Timeline` (waveform + navigator, auto-pan-while-playing), `VideoPlayer` (skip-over-removed-regions playback via `asset://`).

**Windows support**: genuinely shipped (NSIS `.exe` + `.msi`, both **unsigned**), first-class in `binaries.rs`'s target matrix, but **weaker CI coverage** — the main `ci.yml` Rust job runs only on `ubuntu-latest` with sidecars stubbed (never links real ffmpeg); the Windows build is a separate `workflow_dispatch`-only job not run on every PR. `tauri.conf.json`'s bundle config has **no Windows-specific keys at all** (no NSIS/WiX/signing config) — relies entirely on Tauri defaults.

**Multi-track/sync model — does NOT generalize to a real timeline** (see §4 for full detail): it is a single-shared-`CutList`-plus-per-track-scalar-offset system for a fixed synchronized camera/audio rig, not a tracks-of-independently-editable-clips model. MP4 export is single-source only (linked tracks never reach `export_mp4.rs`); only FCPXML export surfaces multiple tracks, and only as connected clips off one primary spine.

**Tests**: 67 inline Rust unit tests (`#[cfg(test)] mod tests` in each module — `probe.rs` 8, `audio.rs` 5, `vad.rs` 15, `cutlist.rs` 7, `timecode.rs` 11, `export_mp4.rs` 8, `export_fcpxml.rs` 12; none in `binaries.rs`/`commands.rs`/`waveform.rs`) + 41 vitest tests (`cuts.test.ts`) = the README's "108 tests" badge, confirmed accurate. `examples/smoke.rs` is a manual CLI smoke-check, deliberately an `example` (not `bin`) so it isn't bundled. No integration tests invoke a real ffmpeg/ffprobe subprocess; `commands.rs`'s orchestration/caching/race-guarding logic has no dedicated tests.

## 4. Duplicate functionality

Both repos independently solve overlapping problems; the unified app must pick one implementation per concern rather than keep both:

- **ffprobe/media-metadata extraction**: capcut-mate's `pymediainfo`-based `VideoMaterial`/`AudioMaterial` probing (`local_materials.py`) vs. autocut's direct `ffprobe -show_streams -show_format` JSON parsing (`probe.rs`). **Decision**: adopt autocut's approach (direct ffprobe JSON, no MediaInfo dependency) since it's already a clean, tested Rust module and avoids an extra native dependency (`pymediainfo`/libmediainfo).
- **Resumable HTTP download**: implemented **three separate times** within capcut-mate alone (`src/utils/download.py`, `src/utils/draft_downloader.py`, `desktop-client/nodeapi/resumableDownload.js`), with independently-drifted retry/backoff constants. The unified project needs exactly one Rust download module.
- **Draft path / installed-app detection**: capcut-mate has this in `desktop-client/nodeapi/draftPathDetect.js` (JS/Electron); nothing in autocut addresses this (autocut has no concept of CapCut at all). Not truly duplicated, but the unified project needs a single Rust implementation informed by capcut-mate's heuristic.
- **Timeline/cut-region data model**: capcut-mate's `Timerange`/segment-on-track model (µs-based, arbitrary clips, general layout, no built-in "keep/remove" semantics — it's a general edit-graph) vs. autocut's `CutList` (f64-seconds, always exactly tiles `[0,duration]` as alternating keep/remove — it's a specialized silence-removal representation, not a general timeline). These are **not interchangeable** — the unified project's own `project.json` timeline (per master-prompt §5/§10) must be a new, general clip-on-track model; autocut's `CutList` becomes one *input* to that model (an edit-plan/operation list), and capcut-mate's segment-on-track model is the closer structural ancestor of the final design, adapted to be non-destructive and ID-referenced.
- **Waveform generation**: capcut-mate has none; autocut has `waveform.rs`. No conflict — reuse the concept, reimplement independently.
- **VAD/silence detection**: capcut-mate has none (it only positions/times material the caller already decided on); autocut's `vad.rs` is the sole implementation. No conflict.
- **Video rendering**: capcut-mate's `gen_video` renders via **Windows RPA driving the real Jianying app** (produces a CapCut-compatible, feature-complete render including all native effects/masks/animations); autocut's `export_mp4.rs` renders via **direct ffmpeg concat+re-encode** (only understands cut regions, no effects/masks/captions/keyframes composited in). These are fundamentally different rendering strategies solving different problems — the unified app needs **both**, as described in master-prompt §32 ("do NOT rely solely on CapCut for final video") and §29-31 (CapCut export is a separate adapter). They are complementary, not duplicative, once explicitly separated into "Local FFmpeg Render Engine" (autocut-derived) vs. "CapCut Draft Export + optional automated render" (capcut-mate-derived).

## 5. Incompatible components

- **Timebase units**: capcut-mate is **i64 microseconds** end-to-end; autocut is **f64 seconds** end-to-end (with a separate rational-frame layer only for FCPXML). These cannot be merged without an explicit conversion layer at every boundary between the two lineages of code. The target project's own decision (master-prompt §67: "prefer integer microseconds") sides with capcut-mate's convention — **autocut-derived Rust modules will need every internal f64-seconds field rewritten to i64 µs**, not just wrapped, since `1e-9`-epsilon float-comparison test assertions throughout autocut's test suite don't translate to integer-exact assertions.
- **Multi-track philosophy**: autocut's "one shared CutList + per-track scalar offset for a fixed rig" model (§2, §4 above) is structurally incompatible with the general Video/Audio/Caption/Image/Overlay/Effect multi-clip timeline the master prompt requires (§10, §39). It cannot be extended in place — the new timeline engine needs an entirely new core data model (tracks-of-independently-editable-clips), with autocut's sync/offset logic surviving only as a *feature* built on top (e.g., a "linked/grouped clips" or `SyncGroup` concept per master-prompt §39), not as the foundation.
- **Rendering strategy**: capcut-mate's `gen_video` requires a live, interactive Windows desktop session with a licensed, pre-installed China-region Jianying Pro app idling on its home screen, and drives it via hardcoded-coordinate mouse clicks and China-locale UI-Automation control-description strings (`jianying_controller.py`). This is **not portable** to a generic end-user's machine as a background/headless operation, and is not validated at all against the international CapCut desktop app's UI tree (different app, different window title, unverified control descriptions). It cannot be shipped as "the" render path for a general-audience Windows app; it can at most become an **optional, clearly-labeled "Export via Jianying" power-user feature** gated behind detecting a real Jianying Pro install, with local FFmpeg rendering (autocut-derived) as the default, always-available path.
- **Deployment model**: capcut-mate is architected as a **stateful HTTP server** (FastAPI, in-process caches/locks/singletons, background asyncio loops, SQLite job store) meant to run continuously and serve multiple concurrent draft sessions over the network. The target app is a **single-user local desktop app** (master-prompt §2: "prefer local IPC rather than HTTP for internal components", "should NOT require Docker"). capcut-mate's HTTP/FastAPI layer itself is not reusable as-is; only the pure-Python business logic underneath (draft engine, service functions minus the HTTP/queueing/caching scaffolding) is relevant, and even that needs either a from-scratch Rust port or a tightly-scoped local sidecar (per master-prompt §3) rather than the current always-on server.
- **Cloud storage dependency**: capcut-mate's COS/OSS/TOS upload flow (`upload_file.py`, `cos.py`/`oss.py`/`tos.py`) assumes a China/APAC cloud-storage backend is available and configured; the target app is local-first/offline-capable (master-prompt §61) and has no need for remote object storage in its core flows. This entire subsystem is out of scope for the unified product except possibly as a much-later, optional "cloud sync" feature.
- **License boundary inside capcut-mate itself**: `desktop-client/` (MIT, "gogoshine", 2025) is a different license and author than the Apache-2.0 main tree (NOTICE: pyJianYingDraft © Gary Guan 2024, modifications © Hommy 2026) — code from each sub-tree must be attributed/tracked separately, they are not interchangeable under one license header.

## 6. Technical risks

1. **RPA-based rendering is inherently fragile and non-portable.** `jianying_controller.py` clicks hardcoded screen pixel coordinates and matches China-region Jianying Pro's exact control-description strings; any Jianying UI update can silently break it, and none of it has been validated against international CapCut. If the unified app offers a "render via installed CapCut" feature at all, it needs to be built and tested from scratch against the *actual* target CapCut build, treated as inherently best-effort/optional, and never the only render path.
2. **autocut has no license.** Confirmed via recursive filesystem search (no LICENSE/COPYING file anywhere) and GitHub API (`"license": null`). Under default copyright law this means no one but the author has rights to copy/modify/redistribute this code. **This blocks literal code reuse from autocut until either (a) the author grants a license, or (b) all autocut-derived functionality is independently reimplemented from the design description in this document without copying source.** Treat every "port from autocut" task in the implementation plan as "reimplement based on autocut's documented design," not "copy autocut's files," unless this is resolved.
3. **Timebase mismatch requires a full rewrite, not adapter glue, for any autocut-derived module.** f64-seconds → i64-µs is pervasive (every struct field, every test assertion). Budget this as original Rust implementation work informed by autocut's algorithms, not a quick wrapper.
4. **capcut-mate's in-process singleton state model doesn't map to a desktop app's lifecycle cleanly.** `DRAFT_CACHE`, `DraftLockManager`, `VideoGenTaskManager` assume a long-lived server process serving many concurrent HTTP clients; a desktop app has different lifecycle/persistence needs (crash recovery per master-prompt §86, single-user, project-file-based). The draft *data model* ports; the *caching/locking/task-queue scaffolding* around it should be redesigned around the app's own project/job-manager architecture (master-prompt §43) rather than ported.
5. **China-region vs. international CapCut format drift is unverified.** Nothing in either repo confirms that `draft_content.json`'s schema, the sticker/花字 catalogs, or the RPA control descriptions are valid against the international CapCut desktop app (only Jianying Pro China was evidently used/tested by capcut-mate's authors). This must be independently verified (ideally by round-tripping a generated draft through a real installed CapCut build) before the CapCut adapter is considered reliable — treat draft-format compatibility as an assumption to validate early (Phase 9), not a given.
6. **Multi-worker/concurrency correctness of capcut-mate is questionable even in its own original deployment** (`--workers 4` requested but apparently unconsumed by `main.py`, with process-local singleton state that would silently misbehave if multi-worker *were* somehow active) — not a risk to the new project directly (the HTTP layer isn't being reused), but a signal that the underlying service-layer code has not been rigorously validated under concurrency, so its logic should be treated as "probably correct for single-threaded/single-session use," not blindly trusted for a Rust rewrite that might introduce real parallelism.
7. **ffmpeg/ffprobe binary provisioning needs a fresh decision.** autocut's approach (BtbN pinned release, manually rotated periodically, no macOS checksum) is only semi-hermetic and carries an ongoing maintenance burden (documented incident of a stale pin breaking builds). capcut-mate bundles a single `ffprobe` binary of unstated provenance in Docker. The unified Windows-only app should pick one clearly-documented, checksum-verified FFmpeg source and version (master-prompt §59) rather than inherit either as-is.
8. **Sticker/花字 catalogs will not work out of the box.** `config/sticker.json`'s CDN URLs are time-signed and already decaying; nothing refreshes them. If the caption/sticker feature set is wanted, the unified app needs its own catalog-sourcing strategy (either a fresh scrape with a refresh mechanism, or dropping sticker support to CapCut-native stickers only, added manually by the user in CapCut post-export).
9. **Windows CI coverage gap inherited as a lesson, not a risk to port.** autocut's Windows build is only manually triggered, not part of per-PR CI, and unsigned. The unified project (Windows-only, primary target Windows 11) must have real per-PR Windows CI from the start (master-prompt §65) — this is a process risk to avoid repeating, not a component to reuse.
10. **No automated frontend/backend type-contract validation in autocut** (`types.ts` hand-mirrors Rust structs with a comment, no codegen). The unified project's IPC surface will be much larger (full timeline, AI edit plans, CapCut adapter, job system) — inheriting a manual-sync convention at that scale is a correctness risk; adopt `specta`/`tauri-specta` or equivalent from the start (master-prompt §66 "strict TypeScript, typed IPC payloads").

## 8. Integration strategy

Given the license and architecture findings above, the integration is **not** "merge two codebases" but **"build one new Rust/Tauri/Svelte application, informed by capcut-mate's draft-engine design (ported/adapted, Apache-2.0-compliant) and autocut's media-engine design (reimplemented, pending license resolution), sharing nothing at the code level except where explicitly permitted."**

1. **Core timeline/project engine — built new**, in Rust, using the master prompt's `project.json` schema (§5) as the source of truth. This is neither repo's model as-is: it needs capcut-mate's general segment-on-track flexibility (arbitrary clip placement, effects/masks/keyframes) but autocut's non-destructive/ID-stable philosophy and the target's i64-µs timebase.
2. **Media analysis engine (VAD/silence/waveform/probe)** — new Rust modules under `src-tauri/src/media/`, `.../vad/`, `.../audio/`, designed after autocut's documented algorithms (two-phase VAD scoring/segmentation, hysteresis thresholds, concat-based cutting, peak-per-bin waveform) but written from scratch in i64-µs and integrated with the new project's `EditPlan`/timeline-command model (master-prompt §18) rather than autocut's single-shared-CutList model. The `voice_activity_detector` crate itself (a separate, independently-licensed dependency) can be pulled in directly regardless of autocut's own license.
3. **CapCut/Jianying draft engine** — a Rust port of `src/pyJianYingDraft/`'s class model (`ScriptFile`/`Track`/segments/materials/animations/keyframes), preserving the µs timebase and the "collect materials on add_segment" pattern, exposed as the `capcut` adapter crate (master-prompt §29: `create_draft`, `add_video`, `add_audio`, `add_caption`, ..., `save_draft`, `export_draft`). This is the most direct, highest-confidence port since capcut-mate's license permits it and the data model is a natural fit.
4. **CapCut/Jianying installation + draft-path detection** — reimplemented natively in Rust from `draftPathDetect.js`'s documented heuristic (§3 above), extended to also probe for the international **CapCut** folder name on Windows (capcut-mate's own Windows path list never did this — a gap this project should close rather than inherit).
5. **RPA-driven automated rendering via the installed CapCut/Jianying app** — **deferred / optional, P2-or-later feature**, not part of the P0/P1 core. If pursued, it must be built and validated against the *actual* target CapCut build (not assumed compatible with capcut-mate's Jianying-Pro-China findings), using a Rust UI-automation crate (`windows-rs` + UI Automation COM APIs) rather than the Python/pyautogui approach. The **primary, always-available render path is local FFmpeg** (master-prompt §32), informed by autocut's concat-based cutting technique but extended to a full `RenderGraph` (§69) supporting composited multi-track output, effects, and captions — something neither repo's render path currently does.
6. **FCPXML export** — reimplemented from autocut's documented rational-timecode and connected-clip design (`timecode.rs`, `export_fcpxml.rs`), generalized to export from the new multi-clip timeline model rather than the single-shared-cutlist model.
7. **No Python sidecar for capcut-mate logic.** Given the draft engine is a moderately-sized, self-contained, well-understood data-model library (not deeply coupled to FastAPI, cloud storage, or RPA), a **full Rust port is preferred over a Python sidecar** (master-prompt §3 allows a sidecar "if required" — here it is not required, since the reusable core doesn't depend on the parts of capcut-mate that would justify keeping Python, namely FastAPI routing, cloud storage SDKs, and RPA). This avoids bundling a Python runtime entirely, simplifying Windows packaging and satisfying master-prompt §3's "never require pip/python install" mandate more cleanly than a sidecar would. Cloud storage (COS/OSS/TOS), the HTTP layer, the LLM-tool-calling string-encoded API shape, and the RPA controller are all explicitly **not** ported — they're artifacts of capcut-mate's original SaaS product, not needed by a local desktop app.
8. **Licensing gate on autocut reuse.** Before Phase 5 (AutoCut integration) begins, either resolve the license question with the autocut author, or confirm (as a checkpoint, documented in `docs/upstream.md` per master-prompt §72) that the Phase-5 implementation was written independently from this audit's design notes rather than copied from `vendor/autocut/src-tauri/src/*.rs`.
9. **Keep `vendor/capcut-mate` and `vendor/autocut` as reference-only, untouched clones** (master-prompt §72 "keep original repositories available for reference"), never imported directly into `src-tauri/`/`src/` build paths — all reuse happens via deliberate porting/reimplementation into the new tree, tracked in `docs/upstream.md`.
