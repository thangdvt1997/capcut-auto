## Audit summary (done before any code, per the upgrade spec's own §30 instruction)

Full audit given to the user directly in conversation on 2026-09-06 — not duplicated here verbatim, summarized:

- **CapCut integration**: real, already built (Phase 9 of the original plan) — but architecturally **direct draft-file writing** (`Project → CapCutExportGraph → CapCutAdapter → real draft JSON on disk`), **not GUI/RPA automation**. The upgrade spec's own §12/§15/§16 (CapCut Automation Layer, Worker/Resource Management, Failure Recovery from "CapCut crash"/"CapCut không mở") all assume a GUI-automation model. **User's explicit decision (2026-09-06): keep the direct draft-file approach, do NOT build RPA/GUI automation.** This makes §15's CapCut Worker Pool and most of §16's CapCut-process-crash recovery scenarios inapplicable by construction — there is no live CapCut process to crash or lose track of. Any future decision to revisit RPA is a separate, explicit product decision (same open item already tracked in `IMPLEMENTATION_PLAN.md`'s Phase 9 section) — not something this upgrade silently reopens.
- **AI integration**: real, already built (Phase 10) — provider-agnostic (`ai::provider`), `EditPlan` closed-schema pipeline, Smart Edit, NL command box, AI-assisted highlight detection, B-roll suggestion, media tagging. No streaming, no automatic retry, no token/cost tracking yet.
- **Job/queue/worker**: real, already built (Phase 11) — `batch::manager`/`batch::pipeline`, one worker thread per batch, sequential, real pause/resume/cancel/retry.
- **Templates**: real, already built (Phase 11) — `templates::mod::Template`, 8 built-ins + custom, save/import/export. No versioning, no intro/outro/watermark/background-music fields, no asset-by-id references yet.
- **Database**: `db::` (SQLite media index, separate from `project.json`), `templates::io` (JSON-file-per-template). No history/job-log table yet.

**User's confirmed direction (2026-09-06)**: implement phase-by-phase per the upgrade spec's own suggested breakdown, verifying and reporting back after each phase before starting the next. The phases below are *adapted* from the spec's own §31 breakdown to reflect what's already real vs. genuinely new — not a verbatim copy, since large parts of the spec's own "Phase 1/2" already exist.

## Phase U1 — Asset Library, Template enhancements, Multi-template batch

- [x] Asset Library (§17): a real catalog for intro/outro/logo/watermark/music/sound-effect/overlay/font/subtitle-style/transition-preset/background, each referenced by a stable id (not a hardcoded path). CRUD (add/list/remove), local-file-backed (mirrors `templates::io`'s existing storage-location convention).
  - New `crate::assets` module (`src-tauri/src/assets/{mod,io,error}.rs`): `AssetKind` (closed enum, §17's exact 11-kind list), `Asset { id, kind, name, file_path, created_at, tags }`, `new_asset(kind, name, file_path)` (real existing-file check via `Path::is_file()`, rejects a nonexistent/non-file path before ever registering it). Storage: `$APPLOCALDATA/assets/<id>.json`, atomic temp-file-then-rename writes — deliberately the same simpler JSON-file-per-item convention `templates::io` already uses (not a `db::MediaLibrary`-style SQLite table): this catalog is a small, curated, user-populated list (a handful of "the logo"/"the outro"/"my music track" entries), not a bulk-import/searchable media index, so SQLite's query/pagination machinery would be unused weight. Files are referenced by absolute path, never copied into app-data (same convention `project::MediaItem::source_path` already uses for external media).
  - Tauri commands (`commands/assets.rs`, registered in `lib.rs`): `list_assets(kind: Option<AssetKind>)`, `add_asset(kind, name, file_path)`, `remove_asset(asset_id)`, `update_asset(asset_id, name?, file_path?, tags?)`.
  - **Which kinds are really consumed vs. structural-only** (documented in `assets::mod`'s module doc comment): **real** — `Intro`/`Outro` (referenced from `Template::intro`/`outro`, resolvable to a real video file); `Logo`/`Watermark` (an image file, referenced from `Template::watermark`); `Music` (an audio file, referenced from `Template::background_music`, could feed `AudioClipSettings`/`AudioRole::Music` once a caller builds a project from a template). **Structural-only** (§17 lists them, no consuming feature exists yet anywhere in this codebase — same honest treatment `templates::mod`'s own `TransitionSettings`/`SportsOverlaySettings` already use): `SoundEffect`, `Overlay`, `Font`, `SubtitleStyle`, `TransitionPreset`, `Background`. `SubtitleStyle` was deliberately kept as a bare `file_path` reference rather than special-cased to reference an existing `CaptionStyle` id — `Template::caption_style` is already a whole owned, fully-real `CaptionStyle`, so there's no real consumer this kind would plug into today.
  - Catalog starts empty — no built-in seed assets, unlike `captions::styles`/`render::presets` — since an intro/logo/music file is inherently a specific user's own asset (§17 frames this as the user registering their own files).
- [x] Template schema enhancements (§3/§20): add `intro`/`outro`/`watermark`/`background_music` fields (each an `Option<AssetReference>` — asset id + a few per-use overrides like watermark position/music volume), and template **versioning** (`version: u32`, a version history so an existing job's `template_id`+`template_version` stays pinned even if the template is later edited — §20's explicit requirement: "Không để user sửa template rồi làm thay đổi các job cũ").
  - `Template` gained 5 new fields, all `#[serde(default)]` (or `#[serde(default = "default_template_version")]` for `version`, defaulting to `1`) so every pre-existing built-in/custom template JSON still deserializes unchanged: `intro: Option<AssetReference>`, `outro: Option<AssetReference>`, `watermark: Option<WatermarkReference>`, `background_music: Option<BackgroundMusicReference>`, `version: u32`.
  - `AssetReference { asset_id }` is used bare for intro/outro (no per-use override needed). `WatermarkReference { asset_id, position: WatermarkPosition }` — `WatermarkPosition` is a new small enum (`TopLeft`/`TopRight`/`BottomLeft`/`BottomRight`/`Center`) rather than reusing `CaptionAnchor` (vertical-only) or `CaptionAlignment` (horizontal-only, for text) — neither already expresses a 2D corner, and no overlay-rendering engine exists yet to warrant a richer offset-based placement. `BackgroundMusicReference { asset_id, volume: f64 }` — linear gain, the same convention `AudioClipSettings::volume` already uses (§3's own YAML example literally writes `volume: 0.2`, matching linear gain, not a 0-100 percentage).
  - Asset-id references are validated against the real Asset Library at save/update time — `templates::validate_asset_references` (pure, unit-tested against a synthetic `HashSet`) checks every referenced id against `known_asset_ids`, which `commands::templates` reads fresh from `assets::io::list_assets` on every call. An unknown id is `TemplateError::UnknownAsset`, matching the existing `UnknownCaptionStyle`/`UnknownExportPreset` pattern exactly.
  - **Versioning/history mechanism**: every built-in and brand-new custom template starts at `version: 1`. A new command, `update_custom_template(template_id, project, input)`, is the only path that edits an existing custom template in place: it bumps `version` to `existing.version + 1`, and — before ever overwriting `<id>.json` — appends the *pre-update* full `Template` snapshot to a new `<id>.history.json` file (`templates::io::append_template_history`/`list_template_history`), a flat JSON array of every previous version, oldest first. Chosen over a `templates_dir/<id>/v<N>.json` subdirectory scheme for simplicity: one read/write per template rather than a directory listing plus N file reads. A new `get_template_version(template_id, version)` command resolves the exact content for a `template_id`+`version` pin: built-in catalog first (always exactly version 1), then the current on-disk custom template (if its version matches), then that template's history file. `update_custom_template` refuses to edit any of the 8 built-ins (`TemplateError::CannotEditBuiltIn`, mirroring `CannotDeleteBuiltIn`'s existing guard) — built-ins stay at `version: 1` forever and never grow a history file.
- [x] Multi-template batch (§11): given N videos and M templates, produce N×M outputs (`video01_tiktok.mp4`, `video01_youtube.mp4`, ...) — extends `batch::` to accept a list of template ids per batch rather than one, reusing the existing single-template pipeline per (video, template) pair, not a new render path. **Done 2026-09-06** (backend only — frontend is a later pass):
  - **API shape**: added a new sibling Tauri command, `start_multi_template_batch(media_paths, template_ids, config)` (`commands::batch`), rather than changing `start_batch`'s existing `BatchPipelineConfig::template_id: Option<String>` shape. `start_batch`'s own single-template call site/signature is completely untouched. The new command resolves every `template_ids` entry's real name (built-in-then-custom, reusing `batch::pipeline`'s own existing `resolve_template` lookup via a new narrow `pub(crate) resolve_template_name` sliver of it) **up front, before any job is created** — an unknown id fails the whole call immediately with `BatchError::UnknownTemplate`, never leaving some jobs pre-doomed deep into a batch.
  - **Job fan-out**: `BatchJobManager::create_multi_template_batch(media_paths, templates: Vec<(id, name)>, base_config)` (`batch::manager`) is a new, pure (no `AppHandle`), directly-unit-testable sibling of the existing `create_batch`, producing exactly N×M `BatchJob`s — one per `(video, template)` pair — reusing `create_batch`'s own `JobState`/`JobHandle` construction and `batch_order`/`job_batch` bookkeeping unchanged; only the enumeration loop differs. Each job's `name` is `"{filename} → {template_name}"` (e.g. `"video01.mp4 → TikTok"`) so the existing, unmodified Jobs UI still shows a sensible per-row name. `run_pipeline` itself was not forked or duplicated — every job still runs through the exact same `batch::pipeline::run_pipeline`.
  - **Output naming**: added one small additive field, `BatchPipelineConfig::output_suffix: Option<String>` (`None` = original `"edited"` default, unchanged for every existing single-template caller). `batch::pipeline::default_output_path` now takes this as an explicit `suffix: &str` parameter instead of hardcoding `"edited"`. A new `pub(crate) fn slugify_template_name(name: &str) -> String` (`batch::pipeline`) — lowercase, every non-ASCII-alphanumeric run collapsed to one `_`, leading/trailing `_` trimmed, `"template"` fallback for an all-punctuation name — is reused (not reinvented; no prior filename-slug helper existed in this codebase to reuse instead) to turn each template's real name into its slug (`"YouTube Shorts"` → `youtube_shorts`, `"Facebook Reel!! (v2)"` → `facebook_reel_v2`). Multi-template jobs get `output_suffix = Some(slug)`, producing exactly §11's `<video_stem>_<template_slug>.<ext>` convention (`video01_tiktok.mp4`).
  - **Concurrency**: unchanged and explicitly confirmed by test — a multi-template batch is still one batch, spawned via the same `spawn_batch_worker` (one dedicated thread, strictly sequential), just with more jobs enumerated up front. No parallel ffmpeg fan-out was introduced.
  - **Partial failure isolation**: confirmed by a real test (`one_failing_video_template_pair_in_a_multi_template_batch_does_not_abort_the_others`, `batch::manager`) — a nonexistent source path's 2 jobs fail with a real error while the other video's 2 jobs (placed *after* the failing ones in processing order) still reach `Completed` with real output files, mirroring this codebase's existing `media::import`/`broll::combine` per-item isolation precedent.
  - **Tests added**: `batch::pipeline` — `resolve_template_name` (built-in + unknown-id), `slugify_template_name` (simple/spaces/punctuation-runs/leading-trailing/unicode/all-punctuation-fallback/idempotence), `default_output_path` with a template-slug suffix. `batch::manager` — N×M fan-out pairing/naming, empty-template-list edge case, a real end-to-end 2 videos × 2 templates = 4 real synthesized-ffmpeg jobs producing 4 correctly-named real output files, and the partial-failure-isolation test above.
  - **Gap/scope note**: `start_multi_template_batch` does not itself validate `template_ids` non-empty (an empty list simply produces a batch with 0 jobs, same "no defensive count validation" posture `create_batch`'s own single-template path already has for `media_paths`); a repeated template id in `template_ids` is accepted, not rejected (produces 2 jobs per video for it — no correctness reason to police it).
  - **Real test-fixture bug found and fixed after this agent's own report** (caught by the concurrent Asset Library agent's own verification, then root-caused and fixed directly rather than re-delegated): the two real end-to-end tests initially used the same constant-sine-tone `synth_named_source` every other test in this file uses — but `tmpl_tiktok`/`tmpl_youtube_shorts` both carry real `silence_settings`, and a pure sine tone has none of real speech's spectral characteristics, so real Silero VAD correctly found **zero** speech segments across the whole clip, `vad::cutlist::build_cuts_from_speech_segments` proposed removing the entire media, and every job correctly failed with `RenderError::EmptyTimeline` — a real, correct pipeline outcome for that input, not a bug in the fan-out/naming logic itself. Fixed by changing `synth_named_source`'s own tone to an amplitude-modulated 220Hz signal (`sine=frequency=220:duration=3,tremolo=f=4:d=0.9`) — empirically verified against this project's real Silero model to produce one confident, whole-clip speech segment — rather than adding an `espeak-ng` dependency or marking the tests `#[ignore]`; every test in this file (including the two that need a real silence-removal outcome) now shares one real, VAD-detectable-by-default fixture with no new external tool dependency.
  - **Frontend compatibility fix**: `BatchPipelineConfig` gaining the new required `output_suffix` field broke `src/components/batch/StartBatchDialog.svelte`'s existing object-literal construction (Phase 11's own single-template Batch Jobs UI) — fixed by adding `output_suffix: null` there (a single-template batch started from that dialog has no per-job suffix to pick; the backend's own `"edited"` default naming applies, unchanged from before this phase).
- [x] Compile, run tests, fix errors, update docs, commit — both Phase U1 bullets (Asset Library/Template enhancements, Multi-template batch) done and merged together. `cargo fmt --check` clean, `cargo clippy --all-targets -- -D warnings` 0 warnings, `cargo test --lib` **841 passed, 0 failed, 4 ignored** (up from 805 pre-upgrade), `cargo test` (full workspace, including `src-tauri/tests/`) all green. `cargo run --bin export_bindings` succeeded. `pnpm run lint`/`check`/`build` all clean (229 files, 0 errors) after the `StartBatchDialog.svelte` fix above.
