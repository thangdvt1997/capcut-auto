## Phase S2 — Wire template asset references into the real build pipeline

Closes the "PARTIAL" gaps found above: `Template::intro`/`outro`/`watermark`/`background_music` currently validate but do nothing.

- [x] A real "apply template to project" step, added directly inside `batch::pipeline` (not a new `commands::templates` command — a template is only ever *applied* as part of building a batch job's project today, exactly where `canvas`/`caption_style`/`silence_settings` are already applied; there is no other real "apply template to an already-open project" entry point in this codebase to extend instead). Three new pure functions, called unconditionally (each a no-op when its own template field is `None`) right after the Editing stage's silence-removal/captions logic and before Rendering, in `run_pipeline`:
  - **`apply_intro_outro`**: real µs-accurate splicing. Both the intro and outro asset's file are probed for real via `media::probe::probe` (never an assumed/hardcoded duration) via a new small helper, `splice_clip`. Design decision (explicitly not silently assumed, per the task brief): spliced onto the **same** `video_track_id`/`audio_track_id` `build_whole_media_project` already created — not a new track — since an intro/outro is ordinary main content, just placed before/after the rest, and there is no existing "insert a clip and shift everything after it" helper anywhere in this codebase to reuse (`timeline::command`'s real command set is trim/cut/delete/split, not insert-with-shift) — a small, direct, well-tested addition rather than a second competing mechanism. Outro is spliced first (appended at the pre-intro content's own end), then intro (which shifts every existing clip — including the just-added outro clip — and every real caption + its word timings later by the intro's own real duration); this ordering only keeps each step's math independent, it has no semantic effect on the final result. An asset that has only video or only audio content correctly only gets a clip on the matching track (`splice_clip`'s own real `probed.has_video`/`has_audio` check), never a silent black video clip or an empty audio clip.
  - **`apply_background_music`**: inserts the referenced music asset as a real new `AudioRole::Music` track spanning the built project's own final content duration (applied after `apply_intro_outro`, so it covers a spliced intro/outro too), with the template's own `volume` (linear gain, matching `BackgroundMusicReference::volume`'s own doc comment) recorded via the existing real `ProjectV1::audio_clip_settings` overlay — the exact mechanism `render::plan` already turns into a real ffmpeg `volume` filter, no second volume mechanism invented. No looping: a music asset shorter than the project just plays once and falls silent for the remainder (an honest, documented simplification — this pass does not add loop-splicing). Ducking is wired up **only** when the resolved template also carries `sports_overlay` (using its already-real `music_ducking` field — `background_music` and `sports_overlay` are independent optional fields, so a template with only `background_music` set mixes the music in at its configured volume, unducked, which is the honest behavior given nothing else on `Template` describes a ducking policy): the main content's own audio track is marked `AudioRole::Voice` (a real, deliberate design choice — nothing else marks it that way, and `commands::render::compute_voice_speech_segments` only ever scores `Voice`-role tracks) and the new music track gets a `ProjectV1::track_ducking` entry copied from `music_ducking`.
  - **The watermark decision (made explicitly, not silently assumed)**: re-checked both options the task brief posed before picking either — and found the premise underlying option (b) ("build a *new* ffmpeg overlay filter step") was actually already false. `render::graph::build_render_graph`'s own `is_visual_kind` already treats `TrackKind::Overlay` completely identically to `TrackKind::Video`/`Image` (chained ffmpeg `overlay` filters, per-clip `ClipSettings::transform_x/y` placement, time-windowed `enable=`) — and `capcut::graph` does the exact same thing for CapCut export (its own module doc comment: "`Overlay` is..." mapped the same way). A real overlay-compositing engine already exists and already covers **both** output paths; the STUDIO_PLAN.md audit's own "no overlay-rendering engine exists to actually composite it" line (and `templates::mod`'s/`assets::mod`'s doc comments repeating a version of that claim) undersold what `render::graph`/`capcut::graph` already do for an `Overlay`-kind track with an `Image`-kind clip — `render::graph`/`capcut::graph` themselves needed no correction (both already described this accurately); `templates::mod`'s (`WatermarkPosition`, `Template::watermark`/`intro`/`outro`/`background_music`) and `assets::mod`'s own doc comments were the ones updated, as part of this pass, to stop describing these fields as validated-but-inert (a small, honest documentation fix, not a re-scoping). So: **`apply_watermark`** adds a real still-image clip on a brand-new `Overlay`-kind track (`render_index` set to one past the highest existing visual track's own render_index, so it always composites on top), positioned by the template's `WatermarkPosition` via a new `watermark_transform` helper — an exact algebraic inversion of `render::plan::build_video_clip_filter`'s own `overlay_x`/`overlay_y` pixel formula, inset by `SafeMargins::default()`'s existing 5%-of-canvas margin fraction (reused, not a second margin convention). This composits for real on **both** the Internal ffmpeg render path (unmodified `render::plan`) and, were a batch-built project ever exported to CapCut (it currently is not — batch jobs only ever render internally, an existing, separate scope boundary, not something this pass changes), the CapCut path too (unmodified `capcut::graph`) — **no gap to flag for either path**. Scope limit, documented and enforced with a real error rather than a silent no-op: only a real still-image asset is supported (`media::import::classify_extension` must resolve to `MediaKind::Image`) — a video/animated watermark would need its own loop/trim handling this pass does not add, and `apply_watermark` returns a clear `BatchError::StageFailed` rather than silently doing nothing for one.
  - Real voice-presence signal for ducking: `commands::render::compute_voice_speech_segments` (previously `fn`, now `pub(crate) fn` — a one-line visibility change, no logic touched) is reused directly by `batch::pipeline`'s own Rendering stage, called only when `apply_background_music` actually marked a `Voice`-role track (so every batch job that doesn't use `background_music`+`sports_overlay` — still the common case — keeps paying exactly the same zero extra cost as before, `&[]`).
  - `PipelineIo`/`PipelinePaths` gained a new `assets_dir` field (`commands::assets::assets_dir`, reused unchanged) so `batch::pipeline` can resolve a template's asset-id references against the real Asset Library — every existing test construction site across `batch::manager`/`batch::pipeline`/`batch::dry_run`/`tests/performance_validation.rs` updated to supply it.

## Phase S3 — Missing presets + manual crop

- [x] **New render presets** (`render::presets::all_presets()`, now 10 entries, up from 7): `youtube_shorts_1080x1920` (dedicated, distinct from `tiktok_1080x1920`), `facebook_reel_1080x1920`, `original` (pass-through source resolution/fps).
  - **YouTube Shorts**: 1080x1920, same real spec as TikTok's preset, but bitrate-controlled at YouTube's own published 1080p30 figure (8 Mbps — YouTube's table is keyed by pixel count, and 1080x1920 has exactly the same pixel count as 1920x1080, so this preset reuses `youtube_1080p`'s own bitrate figure directly, not a guess) with higher-bitrate AAC audio (192 vs TikTok's 128 kbps) — closes the exact gap `tmpl_youtube_shorts`'s own doc comment flagged (reusing `tiktok_1080x1920` directly). `tmpl_youtube_shorts` now references `youtube_shorts_1080x1920`.
  - **Facebook Reel**: 1080x1920 (the real, documented Reels spec). Facebook publishes no recommended-bitrate table the way YouTube does, so this preset stays CRF-based (quality-targeted, CRF 20) like TikTok's own preset rather than inventing a bitrate number with nothing published to check it against.
  - **Original (the one real design challenge)**: `RenderSettings::width`/`height` became `Option<u32>`, `fps` became `Option<Rational>` (previously all three were fixed, non-optional values on every preset). `None` means "no fixed value requested here." The design call that actually matters: reading `render::plan::build_ffmpeg_plan` closely (as the task brief asked) revealed `RenderSettings::width/height/fps` were **never actually the authority for a render's real output pixel dimensions/frame rate** — `build_ffmpeg_plan` reads its base canvas size and `-r` output frame rate entirely from `RenderGraph::canvas` (`ProjectV1::canvas`), never from `RenderSettings` directly; `RenderSettings::width/height` are only ever consulted by `validate()` (sanity-checking, e.g. even/positive). Every *other* preset "just works" today purely because every built-in `Template`'s own fixed `canvas` already matches its referenced preset's fixed dimensions by construction (`templates::mod`'s `canvas_16x9`/`canvas_9x16` helpers) — a real, pre-existing architectural fact, not something this phase changed. Given that, making `width`/`height`/`fps` `Option` needed two real pieces of follow-through, not just a type change: (1) `RenderSettings::validate()` now only checks a dimension/fps when it's `Some` — nothing to validate about a value that isn't fixed at all; (2) the one place that previously hardcoded a fixed canvas *independent of the real source* — `batch::pipeline::run_pipeline`, which built a batch job's project canvas from a resolved template's own fixed `canvas` (or the project default) — now calls a new pure, directly-unit-tested `pass_through_source_canvas(settings, probed)` helper first: when the resolved preset requests pass-through (`width.is_none()`) and the source has real usable probed video dimensions, the project's canvas is built from the source's own real probed width/height/fps instead of the template's fixed one, so the render that follows genuinely passes the source through. Falls back to the template's own canvas (today's exact existing behavior) for every other preset, and for an audio-only/dimension-less source even with the `"original"` preset. `commands::render::start_render_job`'s own single-project path needed no equivalent new plumbing: it already renders whatever `ProjectV1::canvas` the caller supplies, so `"original"` there is pass-through by construction the moment `RenderSettings` tolerates `None` — genuinely a *thinner* gap than the batch path's, not an unaddressed one. `batch::dry_run::run_dry_run`'s own preview output (`DryRunExpectedOutput::width/height`, a `u32` pair, not `Option`, since it's meant to show the caller a real concrete predicted number) resolves the same way: `preset.settings.width.unwrap_or(probed.width)` — the real, already-probed source's own dimensions, not a bare "unknown".
- [x] **Manual per-clip crop**: `ClipSettings` gained a new `crop: Option<ClipCrop>` field (`ClipCrop { x, y, width, height }`, all `f64`), `#[serde(default)]` so every existing saved project deserializes unchanged (`None`). **Unit convention decision**: normalized 0.0-1.0 fractions of the SOURCE MEDIA's own native width/height — deliberately matching `scale_x`/`scale_y`'s own existing convention on the same struct ("a unitless value expressed relative to the media's own native dimensions"), not `transform_x`/`transform_y`'s half-canvas-relative placement units (a different concept — *where on the canvas*, not *which region of the source frame*) and not raw pixels (which would silently go stale the moment the same clip's source is swapped for a differently-sized proxy/re-encode). ### What was built

### The `drawtext` vs. `.ass`/`subtitles=` decision, and why

Read the real style schema (`project::types::CaptionStyle`) and its two existing consumers (`capcut::caption_style.rs`, `src/components/preview/CaptionOverlay.svelte`) before deciding, per the task brief's own instruction not to take the suggestion on faith. `drawtext` won, for real reasons found while reading, not assumed up front:
- `CaptionStyle` already tracks exactly the fields `drawtext` natively supports as filter options (`fontcolor`, `fontsize`, `box`/`boxcolor`, `bordercolor`/`borderw`, `shadowcolor`/`shadowx`/`shadowy`, `alpha`) — a direct, field-for-field mapping, not a lossy reduction.
- An `.ass`-file approach would need genuinely new machinery this codebase has no precedent for (no "write a subtitle file" writer exists anywhere here), plus its own escaping rules and ASS override-tag dialect (`\an`/`\pos`/`\c&Hxxxxxx&`/`\bord`/`\shad`) to hand-generate correctly — meaningfully more machinery for the same real-world result `drawtext` already gives directly.
- `drawtext`'s one real gap relative to `.ass` is per-word/per-line karaoke highlight timing — already out of scope per `docs/feature-matrix.md`'s own pre-existing "Active-word/karaoke highlighting" row (preview-only; none of the three export paths bake per-word timing into their output) — this phase doesn't change that, and didn't need to.

### Honest scope calls (documented in `render::captions`'s own module doc comment, not just here)

- **Font resolution**: no font-management/catalog system exists in this codebase (`capcut::caption_style`'s own doc comment notes the identical gap for the CapCut path: "no font-resource catalog is ported this pass"). This phase does not invent one. `CaptionStyle::font_family`/`bold`/`italic` pass through as a real ffmpeg **fontconfig pattern** (`font=<family>[:style=Bold][:style=Italic][:style=Bold Italic]`) — a real, verified mechanism, not a guess: both this project's dev/CI ffmpeg (`ffmpeg -version` on the WSL dev machine) and the bundled Windows sidecar binary (`src-tauri/binaries/ffmpeg-x86_64-pc-windows-msvc.exe`, inspected directly via `strings` on the actual shipped binary) report `--enable-fontconfig --enable-libfreetype` in their real build configuration. When fontconfig can't resolve a requested family/style on the end user's machine, it silently substitutes its own default — every OTHER real style property (color/size/position/background/outline/shadow/opacity) still applies regardless. Matches Phase S2's watermark work honestly scoping itself to static images only — a real, working, honestly-bounded fallback, not a silent no-op and not a false claim of exact font-family/weight fidelity.
- **Shadow blur**: `CaptionStyle::shadow.blur` (a soft diffuse radius) has no `drawtext` equivalent — `drawtext` only supports a flat, unblurred offset-copy shadow (`shadowcolor`/`shadowx`/`shadowy`, all applied for real). `blur` itself does not carry through to the burned-in render; documented once, in code, rather than silently dropping the whole shadow or claiming full fidelity.
- **Position convention — a real judgment call, not an oversight**: `CaptionPosition`'s own doc comment claims its `offset_x`/`offset_y` share `ClipSettings::transform_x/y`'s "positive-y-is-up" convention, but the actual shipped live-preview renderer (`CaptionOverlay.svelte`) does **not** negate `offset_y` when converting it to a CSS `translateY` (a y-down pixel space — the same direction ffmpeg's own pixel space uses) — it passes it straight through. This phase deliberately matches the live preview's own *actual, shipped* pixel behavior (no sign flip) rather than the type doc comment's stated intent, per the task brief's own instruction to reuse whichever convention is already established so burned-in captions land where the live preview already showed them. A user who already nudged a caption's `offset_y` slider while watching the live preview gets the identical visual result burned in.
- **`shadowx`/`shadowy` are the one position value NOT expressed as an ffmpeg expression**: `ffmpeg -h filter=drawtext` documents both as plain `<int>` options (unlike `x`/`y`, which are `<string>` and accept expressions referencing `w`/`h`/`text_w`/`text_h`) — so a shadow's half-canvas-unit offset is resolved to a concrete pixel integer at plan-build time using the real canvas dimensions, while the caption's own `x`/`y` position stays a resolution-independent ffmpeg expression (the same "let ffmpeg's own expression evaluator resolve something only known at filter-run-time" idiom `render::plan` already uses for `rotate=`'s `ow=rotw(angle)`).

### Text escaping — verified against a real ffmpeg build, not assumed from the docs

Fetched ffmpeg's own `doc/filters.texi` "Notes on filtergraph escaping" section directly (not paraphrased from memory) to get the authoritative two-level escaping algorithm, then verified the derived algorithm against a real ffmpeg build (`ffmpeg -v debug`'s own "Setting 'text' to value ..." log line, plus real rendered-frame screenshots) before trusting it: a raw `\` needs 4 backslashes, a raw `'` or `:` needs the option-value level's escape (`\` -> `\\`, `'`/`:` -> `\` + char) applied a SECOND time at the filter-description level (since embedding a `drawtext=...` filter directly inside one already-assembled `-filter_complex` argument is exactly the "whole filter description" context those docs describe) — landing on 3 backslashes for `'`, 2 for `:`; `,`/`;`/`[`/`]` are only special at the filter-description level, so one backslash suffices. A real embedded newline byte (not the two-character `\n` escape sequence — verified that ffmpeg's own `drawtext` does *not* treat a literal two-char `\n` as a line break) is left untouched entirely and renders as a genuine new line via FreeType's own line-breaking, verified with a real two-line rendered screenshot. `expansion=none` is always set on every caption's `drawtext` filter — a caption whose real text contains a literal `%` (e.g. "50% off") would otherwise trigger ffmpeg's own `%{...}` expansion syntax, logging "Stray %" and silently truncating the text at that point (verified: reproduced the exact failure, then confirmed `expansion=none` fixes it) — captions have no legitimate use for `drawtext`'s own timecode/frame-number expansion syntax anyway, since timing is already handled by `enable=`.

One real bug caught by this verification process before it shipped: an early version of the fontconfig `style=` suffix used only a single escaped backslash before the embedded colon (matching what looked like a working pattern from an earlier, quote-wrapped experiment) — a real ffmpeg run immediately surfaced `Error applying option 'style' to filter 'drawtext': Option not found` (rc=8, a hard failure, not a silent misrender). Fixed by routing the whole `family:style=X` string through the same `escape_drawtext_text` every caption's own text gets, rather than a bespoke single-backslash version — now covered by a dedicated test asserting the double-backslash form.

## UI Redesign Audit + Phase D0–D8 Plan (`promt.md`'s 3-tab shell, Design System, Worker/Slot manager)

Read-only audit, no code written — mirrors the same audit-before-code discipline every other spec in this project has followed.

### 1. Current app shell/navigation

`src/App.svelte` is a single-screen shell, **not tabbed today**: `TopBar` + a vertical `ResizableSplit` (top: horizontal split of `LeftPanel` | `CenterPreview` | `RightPanel`; bottom: docked `TimelinePanel`, the real multi-track NLE — by far this app's single largest engineering investment). `LeftPanel`/`RightPanel` each have their own internal tab strip already (Media/Transcript/Templates/AI; Inspector/Captions/AI Edit/Properties). In other words: the settings/automation/asset-management surface `promt.md` wants reorganized into Tab 2/Tab 3 **already exists today, fully implemented**, just as ~13 separate dialogs, not unbuilt scope.

### 2. Existing design-system-adjacent code

**No shared component library exists.** Confirmed by sampling `CapCutSettingsDialog.svelte`/`AutomationRulesDialog.svelte`: each hand-rolls its own backdrop/dialog markup, its own Escape-key handler, and a full component-scoped `<style>` block from scratch — **18 such dialogs total**, ~150–700 lines each. What does exist and is reusable: `src/styles/globals.css`'s real dark-theme HSL token set (`--background`/`--surface`/`--border`/`--foreground`/`--muted`/`--pos`/`--neg`/`--accent`/etc.), a 3-step radius scale, and exactly two shared classes: `.btn`/`.btn-ghost` (no Primary/Secondary/Danger variants yet, despite `promt.md`'s own explicit 4-tier button hierarchy ask). Conclusion: this is a "build ~20 components from nothing, then decide what to do with 18 existing hand-rolled dialogs" situation, not an "extract what's there" situation.

### 3. Job Queue: dialog today, docked panel in the mock

`BatchJobsDialog.svelte` (live-updating Jobs table off a real `batch:progress` event, per-row Pause/Resume/Cancel/Retry) is a modal dialog, matching this app's established pattern. `promt.md`'s own §28 mock shows the Job Queue as a **permanently-docked bottom panel** of the main window — a real structural navigation change (modal → always-visible panel competing for space with the video preview/script editor and the already-docked Timeline), not a visual reskin. Needs an explicit decision (Phase D0 below).

### 4. Worker/Slot concurrency — a real, confirmed architectural conflict

`batch::manager`'s own module doc comment: **one dedicated worker thread per *batch*, strictly sequential within that batch** (concurrency = 1 *inside* a batch; unbounded distinct batches can run side by side) — a deliberate choice, the same design that satisfies master prompt §50/§85's "no 20 simultaneous ffmpeg processes" concern. `promt.md` §5 asks for a **fixed-size pool of N worker slots**, each independently pulling *individual video jobs* (not whole batches) off *one shared global queue*, with a real "Max concurrent videos: 3" cap — genuinely different from what exists. Before any UI can honestly show "Workers: 3, Running: 3" per the mock, someone has to decide: rearchitect `batch::manager` into a real N-slot pool (a genuine backend rewrite, needing its own new global ffmpeg-concurrency cap to avoid reintroducing the exact problem the current design avoids), or keep today's model and have the UI honestly show "N batches running, 1 file at a time each" (cheaper, but not what the mock depicts, and "max concurrent videos" wouldn't have real teeth). **This rivals the CapCut RPA-vs-direct-export decision in weight** — it needs the user's own explicit call, not an assumption.

### 5. A second architectural fork: does Tab 1 replace or wrap the existing Timeline NLE?

`promt.md`'s §28 Tab-1 mock (video preview | script/subtitle editor rows | pipeline stepper | job queue | status bar) shows **no multi-track timeline, no Media Library, no Inspector** — a linear batch-automation pipeline shape, not a free-form multi-track editor. The current app IS a real multi-track NLE (drag/drop across V1/V2/A1/CC tracks, zoom/scroll, keyframes, manual crop, sync groups — the accumulated Phase 4-through-Studio-S4 investment). Two honest readings: (a) Tab 1 = today's 4-pane layout + docked Timeline, restyled, with the stepper/queue elements added around it (cheaper, preserves the NLE); or (b) Tab 1 = the mock literally, demoting/hiding the Timeline/Media Library/Inspector for everyday use (expensive, strands a lot of working, tested functionality). Needs an explicit decision before Phase D3 design work starts, for the same reason as #4.

### 6. i18n scale

~1092 real keys today (`en.json`/`vi.json`, both hand-written), house rule: every new string gets a real key in both files at build time. A redesign at this scale (3 tabs, ~20-component design system with multiple states each, a 10-category settings sidebar, a new Worker/Slot dashboard, a new Activity/Log panel) plausibly adds several hundred new keys across both files — a real, easy-to-underestimate cost, not a by-product.

## Phase D4a — Worker/Slot concurrency rearchitecture (promt.md §5, blocking product decision now resolved)

Resolves the "UI Redesign Audit" section's own §4 blocking question above: **the user explicitly chose "rearchitect `batch::manager` into a real N-slot worker pool"**, not the cheaper "keep one-thread-per-batch, rescope the UI's own 'Workers' claim" alternative. Backend-only (`src-tauri/` plus the auto-generated `src/types/bindings.ts`) — no frontend consumes any of this yet (that's Phase D4's own UI half, still unbuilt).

### What changed, and what deliberately didn't

`batch::manager`'s original design — one dedicated worker thread per `start_batch` call, strictly sequential *within* that batch, unbounded *across* distinct batches — is replaced with a real, fixed-size pool of `max_concurrent_jobs` worker threads pulling from **one shared, cross-batch queue of individual jobs**, exactly matching `promt.md` §5's own "Workers: 3, Running: 3... Max concurrent videos: [3]... queue manager must automatically pull the next job when a worker finishes" concept. Every job from every batch — single-template, multi-template N×M fan-out, a history re-run, a retry — now goes through the same one queue, and can genuinely run concurrently with any other queued job, up to the pool's own configured cap. `batch::pipeline::run_pipeline` (the actual per-job work function) needed **zero changes** — only how/when a job gets picked up changed.

**Design chosen, and why**: a plain `Mutex<VecDeque<String>>` (job ids) + `Condvar`, added directly to `BatchJobManager` (`queue`/`queue_cv`, plus `active_workers`/`worker_pool_size` `AtomicUsize` counters for live status reporting) — matching every other piece of shared mutable state already in this module and in `RenderJobs`/`TranscriptionJobs` (`Mutex<HashMap<...>>` + `Arc<AtomicBool>`), not a channel or async-mpsc mechanism (nothing else in this codebase's job managers uses one, and introducing a new concurrency primitive convention for just this one feature wasn't worth it). `BatchJobManager::pop_blocking()` blocks on the queue's own condvar (re-checking a test-only `shutdown` flag every 200ms so a shutdown request is never lost to a wakeup race) and claims a job by incrementing `active_workers`; `mark_job_done()` decrements it once that job reaches a terminal state.

The pool itself is spawned **once**, at app startup (`lib.rs`'s `setup`, right after `BatchJobManager` is `.manage()`d — ordering matters, since each worker thread's own loop body re-fetches `app.state::<BatchJobManager>()` fresh every iteration, the same "capture `AppHandle`, re-resolve state each time" convention `run_job_with_events` already used, rather than trying to smuggle an `Arc<BatchJobManager>` out of Tauri's own state container), via `batch::manager::spawn_worker_pool(&manager, app_handle, max_concurrent_jobs)`. Each of the `max_concurrent_jobs` threads (`tauri::async_runtime::spawn_blocking`, matching this codebase's own established "never block Tauri's command-dispatch thread" convention for long-running job managers) loops forever: `pop_blocking` → `run_job_with_events` (entirely unchanged: real path resolution, `batch:progress` event emission, and history recording, all exactly as before) → `mark_job_done` → loop. `max_concurrent_jobs` has a real, honest default — `BatchJobManager::DEFAULT_MAX_CONCURRENT_JOBS = 3`, literally `promt.md` §5's own worked example — passed as a real constructor argument to `spawn_worker_pool` rather than hardcoded inline; no settings-persistence UI exists yet for this value (matches this task's own explicitly-scoped honest limit), so a real, changeable parameter/default is this pass's full scope here, not a fabricated "configurable" claim.

`start_batch`/`start_multi_template_batch`/`retry_batch_job`/`spawn_batch_worker` **kept their exact existing names and signatures** — every one of `commands::batch`'s Tauri commands, `commands::history`'s two rerun commands, and `automation::manager`'s rule-firing logic call these completely unchanged. Only `spawn_batch_worker`'s own body changed, from "spawn a dedicated thread that runs this batch's jobs sequentially" to "push these job ids onto the shared pool queue" (`BatchJobManager::enqueue_jobs`) — every existing caller of `spawn_batch_worker(app, job_ids)` needed zero code changes. `retry_batch_job`'s `app: AppHandle` parameter is now unused internally (renamed `_app`) rather than removed from the signature, purely to avoid touching `commands::batch::retry_batch_job`'s own call site for no real benefit.

### Pause/resume/cancel/retry under real concurrency — preserved exactly, no simplification needed

Each job's own `cancel`/`pause` `Arc<AtomicBool>` pair (on its `JobHandle`, unchanged) is shared directly with whichever worker thread happens to have popped that job — the flags don't know or care which thread reads/writes them, so pausing/cancelling one job never affects any other job a different worker is concurrently processing, and one worker parked in `batch::pipeline::checkpoint`'s own pause-wait loop never blocks any other worker's `pop_blocking`/`process_job` loop. **This required zero changes to `checkpoint`, `set_paused`, or `cancel`** — the existing per-job-flag design already generalized correctly to N-worker concurrency; it was never actually coupled to the old one-thread-per-batch assumption. `retry_batch_job`'s only real change: a retried job now goes back onto the **same shared queue** every other job comes from (`enqueue_jobs`), not a batch-specific structure — a "batch" is no longer a processing unit at all after this rearchitecture, only a grouping label (`batch_order`/`job_batch`) that `list_jobs`/history still use.

Proven under real concurrency (not just asserted), by a new test: `pause_resume_cancel_and_retry_all_work_correctly_with_multiple_workers_active_simultaneously` runs 2 real local worker threads against 3 real jobs — one paused *before* it's even claimed (parking one worker for the whole test), one that fails immediately (missing source), and one plain job — and confirms the plain job completes and the missing-source job fails **while the paused job is still genuinely parked**, then resumes it (completes normally) and retries the failed one (re-enters the same shared queue, gets picked up by whichever worker frees next, fails again identically for the same still-missing file — this module's own pre-existing, documented retry contract, unaffected by concurrency).

**No pause/resume simplification was needed or made** — worth stating plainly since the task brief explicitly allowed for one if fine-grained correctness under concurrency turned out to be too large to close out safely this pass. It didn't: the existing per-job-flag design was already correct for arbitrary concurrent worker access, with nothing to weaken.

### `get_worker_pool_status` — the real "Workers: N, Running: R, Queue: Q" surface

New Tauri command, registered like every other: `commands::batch::get_worker_pool_status() -> WorkerPoolStatus`, where:

```rust
pub struct WorkerPoolStatus {
    pub workers: usize, // configured pool size (0 if spawn_worker_pool was never called)
    pub running: usize, // workers currently holding a claimed job right now
    pub queued: usize,  // jobs waiting in the shared queue, not yet claimed
}
```

`workers`/`running` are the `worker_pool_size`/`active_workers` atomics above; `queued` is the shared queue's real, live length. This is the exact real backend surface `promt.md`'s dashboard mock needs — without it, no frontend could honestly show real worker/queue numbers (the whole reason Phase D0's own §4 blocking decision existed). Directly unit-tested (`worker_pool_status_reports_pool_size_active_workers_and_queue_length`) through every state transition: empty pool, jobs enqueued, one claimed, one marked done.

### Real cross-batch concurrency, proven with the mirror-image of the OLD bound's own test technique

`tests/performance_validation.rs`'s pre-existing `bounded_concurrency_batch_pipeline_never_runs_more_than_one_ffmpeg_process_at_a_time` proved the OLD design's "never more than 1 concurrent real ffmpeg process per batch" guarantee via real `ps`-based process-count sampling — it calls `run_pipeline` directly in a loop, never through `BatchJobManager`, so it is **completely unaffected by this rearchitecture** and still passes unchanged (verified). The new mirror-image test, `batch::manager::tests::worker_pool_runs_up_to_max_concurrent_jobs_real_ffmpeg_processes_at_once_but_never_more`, uses the identical real `ps`-sampling technique against 3 real local worker threads draining a real shared queue of 6 real synthesized sources (enough that workers genuinely have to be reused, not just "N jobs for N workers"), and asserts a real, sampled maximum of **more than 1** (genuine overlap, the actual point of this rearchitecture) and **at most `MAX_CONCURRENT`** (the real, still-enforced cap) — never fewer than 2 processes observed, never more than 3.

### Honest scope / simplification notes

- **Deliberate, product-decided behavior change**: a multi-template batch's own N×M jobs, and any single batch's own jobs generally, are no longer guaranteed strictly sequential relative to each other — they're now eligible for genuine concurrent execution alongside jobs from any other batch, up to `max_concurrent_jobs`. This is not a bug or a regression; it is the explicit point of the product decision this phase resolves, called out here so it's never mistaken for an oversight.
- **`max_concurrent_jobs` is a real, changeable value, not yet a real, changeable *setting*** — `DEFAULT_MAX_CONCURRENT_JOBS = 3` is passed as a real constructor argument at `lib.rs`'s startup call site; there is still no settings-persistence UI anywhere in this app for a user to change it without a code edit. Matches this task's own explicitly-scoped honest limit (no settings UI exists yet for this value) — not silently pretended to be user-configurable today.
- **Pool shutdown**: the real app's own pool never shuts down mid-run (its worker threads loop forever, same as this codebase's every other long-lived background thread) — `BatchJobManager::shutdown_workers` exists only `#[cfg(test)]`, for this pass's own tests to join their locally-spawned worker threads cleanly; production code never calls it, and none was needed (the app's existing `RunEvent::Exit` handler already force-kills tracked ffmpeg children regardless of which thread spawned them).
- **Test timeout tuning**: the first versions of the two new real-concurrency tests used tighter deadlines (30-90s) that occasionally failed under `cargo test`'s own default parallelism (multiple real-ffmpeg-heavy tests, including this phase's own, competing for CPU at once) despite passing reliably in isolation — not a logic bug, a real contention/timing issue. Fixed by widening every deadline generously (90-180s, matching `tests/performance_validation.rs`'s own documented "deliberately generous, not a tuned micro-benchmark" philosophy) and re-confirming two consecutive full clean `cargo test --lib` runs afterward.

### 1. The real Worker/Slot status widget

New `src/components/batch/WorkerPoolWidget.svelte` — three `Badge`s (Design System, Phase D1) reading `stores/batch.svelte.ts`'s real `workerPoolStatus` (`{ workers, running, queued }`, off Phase D4a's `get_worker_pool_status` command): `Workers: N` (always neutral), `Running: R` (accent when `R > 0`), `Queued: Q` (warn when `Q > 0`). `null` (never fetched yet) renders as `0` in every slot rather than a fabricated placeholder number — a real distinction from "genuinely zero," tracked separately via `workerPoolStatusError`/the widget's own `title` attribute surfacing any fetch error, but not treated as a different visible number (there is no honest non-numeric way to render inside a `Badge` here without a larger redesign than this pass's own scope).

**Polling contract (task brief: "poll on a short interval only while there's reason to... don't poll forever when idle"), implemented as three real, independent mechanisms, not one:**

1. **One unconditional fetch on mount** (`WorkerPoolWidget.svelte`'s own first `$effect`, which reads no reactive state and therefore only ever runs once) — so the widget shows a real snapshot immediately, even if no job is active the moment it appears (e.g. reopening `BatchJobsDialog.svelte` long after everything finished).
2. **A 2-second `setInterval` while `stores/batch.svelte.ts`'s new `anyJobActive` derived is true** (`Object.values(jobsById).some(j => status not in {completed, failed, cancelled})`), started/stopped by the widget's own second `$effect` (keyed on that boolean) — the interval is created and torn down by the *component*, not the store: a plain store class has no lifecycle of its own to hook a timer into, the same reasoning `stores/autoZoom.svelte.ts`'s own doc comment already documented for an unrelated feature (component owns lifecycle, store owns state), followed here rather than reinvented.
3. **Two eager, non-interval refreshes from the store itself**, for the two moments a poll would otherwise show stale numbers for up to 2s: right after `startBatch`/`startMultiTemplateBatch`/`adoptExternalBatch` return successfully (a batch's jobs occupy/queue for real worker slots the instant `start_batch` returns), and right after any job's `batch:progress` event carries it into a terminal status for the first time (`completed`/`failed`/`cancelled` — the exact moment a worker frees up server-side). Deliberately **not** refreshed on every in-flight progress tick (those fire far more often, e.g. per percent) — that would have defeated the "don't waste resources" half of the same requirement for no visible benefit, since `running`/`queued` don't change while a job is merely progressing.

If both `JobQueuePanel.svelte` (Tab 1) and `BatchJobsDialog.svelte` are mounted at once (the dialog opened while Tab 1 stays on screen), two independent widget instances each run their own 2s interval — a small, deliberately-accepted duplication (at most one extra IPC call every 2s) rather than centralizing interval ownership in the store for this pass.

Backdrop-click and the header's `×` always closed the whole dialog unconditionally in the original too, so wiring `Modal`'s `onClose` straight to `automationStore.close()` reproduces that half unchanged.

## Phase D8a — Job crash-recovery *detection* (promt.md §17 "JOB STATE / RESUME")

Backend-only (`src/` untouched — no new/changed `#[tauri::command]`, no new specta-typed struct exposed over IPC, so `export_bindings` was not re-run; confirmed `src/types/bindings.ts` needed no changes). Ran independently of, but in the same shared working tree as, the Phase D8b Activity/Log pass below.

### The honest scope line, stated up front

This is **crash-recovery detection and honest surfacing**, not the fine-grained stage-skip *resume* `promt.md` §17's own worked example describes ("video đã Extract✓ Translate✓ Voice✓ Render✗ … restart app: resume từ Render"). Building true resume would require restructuring how `batch::pipeline::run_pipeline` hands each stage's output to the next — today it is one single, monolithic, run-to-completion function with no concept of "start at stage N, reusing stage N-1's already-computed output"; the in-progress `ProjectV1` being edited lives only in a stack-local variable inside that function, never persisted anywhere a restart could pick back up from (`batch::manager` module doc comment's own "Retry semantics" section already documents this exact same gap for plain in-process retry, which restarts from scratch for the identical reason). Restructuring that is a large, separate, high-risk architecture project on the single most complex subsystem in this codebase (freshly rearchitected for the Phase D4a N-worker pool) — explicitly out of scope for this task, per the task brief. **Nothing in `run_pipeline`'s stage execution logic, its stage-to-stage data flow, or `spawn_worker_pool`'s concurrency machinery was touched.**

What was built instead: detect a job that was mid-flight when the app last crashed/was killed, and honestly surface it — as a real `Failed` entry in the existing `history` table, retryable via the existing, unchanged Retry mechanism (which already restarts from scratch, exactly like every other failure today) — rather than that job silently vanishing with no trace at all. This is the same "was the last exit clean" question `crate::logging`'s own whole-app `.session-active` marker (module doc comment, master prompt §86) already answers at the process level; this is the per-batch-job equivalent, with enough real data attached to make the resulting history row actually re-runnable.

### 1. New table: `in_progress_jobs` (`src-tauri/src/history/inflight.rs`)

A new file in the existing `history` module, extending the exact same SQLite database/connection `history::io`'s own `history` table already uses (`history` module's own storage-location decision, unchanged) — not a new database, not a new connection. Follows `history::io.rs`'s own conventions exactly: plain `&Connection` parameters, no `AppHandle` anywhere, directly unit-testable via `Connection::open_in_memory()`.

Schema: `job_id` (PK), `batch_id`, `job_name`, `input_path`, `config` (the job's full `BatchPipelineConfig`, JSON — everything needed to actually re-run it from scratch), `status`, `stage`, `started_at`. `InFlightJob` is a plain internal Rust struct (not specta-typed/exposed over IPC — this table is purely an internal recovery mechanism the frontend never sees directly; only the resulting `history` row is ever surfaced to it).

Real CRUD: `init_schema`, `upsert_inflight` (a plain `INSERT OR REPLACE` — unlike `history::io::record_terminal`'s own `retry_count`-preserving upsert, there is no auxiliary counter here worth preserving across an overwrite), `clear_inflight`, `list_inflight`. `status_to_str`/`status_from_str` were promoted from private to `pub(super)` in `history::io.rs` so `history::inflight` reuses the exact same `BatchJobStatus` <-> `TEXT` mapping rather than re-deriving a second, parallel one.

`recover_orphaned_jobs(conn)` is the real startup-time consumer: reads every surviving row (each one is, by construction, an orphaned in-progress job from a prior crash/kill), records it as a `Failed` `history::HistoryEntry` with the honest, fixed error message `INTERRUPTED_ERROR_MESSAGE` = *"Interrupted by app restart — click Retry to reprocess from the start."*, reusing the row's own `job_id` as the history row's `id` (so if that job had already failed and been retried once before, this recovery correctly bumps `retry_count` on the same row via `history::io::record_terminal`'s existing upsert, rather than duplicating it) — then clears the `in_progress_jobs` row. `template_version` is honestly `None` (no `templates_dir` available at this point to re-resolve it against — the same "no templates_dir" case `batch::manager::build_history_entry` already produces on its own early-failure path). `duration_us` is a real, best-effort estimate (time between the row's own `started_at` and the recovery scan's own "now", parsed via `chrono`), falling back to `None` if `started_at` somehow isn't valid RFC3339 (defensive only — every real writer always produces one via `crate::project::now_rfc3339()`).

### 2. Wiring into `batch::manager.rs` — purely additive, no rewrite of transition logic

Two new functions, both directly unit-testable-in-spirit via the same "pure core + thin `AppHandle` wrapper" split every other piece of real logic in this file already uses:

- `build_inflight_job(batch_id, handle) -> Option<InFlightJob>` — the pure core, mirroring `build_history_entry`'s own shape but inverted (`Some` only while *not* terminal, vs. that function's `Some` only once terminal).
- `record_inflight_for_job(app, batch_id, handle)` — the real, best-effort write: upserts while non-terminal, clears the row the instant it's terminal. Mirrors `record_history_for_job`'s own posture exactly (never propagates a database error, never affects the job's own already-decided status, just `tracing::warn!`s and moves on) and, deliberately, its own lock ordering (release the job-state lock before acquiring the database connection lock — matched on purpose, since the two functions taking those locks in opposite orders would be a real deadlock risk).

Called from every real state-transition point this manager already has, with zero changes to what those points *do* otherwise:
- **`spawn_batch_worker`** (the one shared entry point `start_batch`/`start_multi_template_batch`/both `commands::history` rerun commands/`automation::manager` already funnel through) — writes each job's first `Queued` row right after enqueueing.
- **`retry_batch_job`** — now routed through `spawn_batch_worker` itself (previously called `manager.enqueue_jobs` directly with an unused `_app` parameter) specifically so a retried job gets its own fresh `Queued` row too, without duplicating the write call.
- **`run_job_with_events`'s own `on_update` closure** — already fires on every real stage transition a job reports (Analyzing/Transcribing/Editing/Rendering/Paused, and the final terminal one); now also calls `record_inflight_for_job` on every tick, which naturally upserts while non-terminal and clears once terminal — no separate terminal-specific call needed there.
- **`run_job_with_events`'s early pipeline-path-resolution failure branch** (a job that fails before `process_job` ever runs, so never reaches the `on_update` closure) — explicitly clears the row too, since this branch forces the job straight to `Failed`.

### 3. Startup wiring (`lib.rs`)

Immediately after `history::io::init_schema` (same connection, same place `MediaLibrary` is already opened/managed), and before `BatchJobManager` is managed / `spawn_worker_pool` is started: `history::inflight::init_schema`, then `history::inflight::recover_orphaned_jobs`, with the recovered count logged via `tracing::warn!` (0 is the overwhelmingly common case — a clean previous exit leaves this table empty). Ordering matters both ways: the `history` table this recovery writes into must already exist, and the recovery scan must finish clearing stale rows before any real job could possibly write a fresh one.

### 4. Real Rust unit tests (`src-tauri/src/history/inflight.rs`)

Schema creation, insert/update/clear of an in-progress row (including "upserting the same job_id again overwrites in place, not duplicates" and "clearing an unknown job_id is a harmless no-op"), ordering, and the startup recovery scan itself: converting a surviving row into a real `Failed` history entry with the exact honest error message and clearing the row afterward; recovering multiple surviving rows at once; leaving an already-terminal, unrelated history entry completely undisturbed; and correctly bumping `retry_count` when recovering a job whose `job_id` already has a prior `Failed` history row from an earlier real failure.

The one real, already-flowing stream that actually matches §15's own worked example (`"10:21:03 Subtitle extraction completed"` / `"10:21:05 Translation started"` — i.e., pipeline stage transitions) is **`batch:progress`**: every batch job already reports its own human-readable current stage over it (`BatchJob.stage`, e.g. `"Analyzing media"`, `"Transcribing"`, `"Removing silence"`, `"Generating captions"`, `"Editing complete"`, `"Rendering"`, and — since `batch::manager::process_job`'s own terminal match arms set `stage` to exactly these words — `"Completed"`/`"Failed"`/`"Cancelled"` too).

### 1. `stores/activityLog.svelte.ts` — new store, not an extension of `batch.svelte.ts`

A new store (not folded into `stores/batch.svelte.ts`) since its own concern — turning stage transitions into a capped, filterable log feed — is genuinely separate from `batchStore`'s own per-job table/dialog bookkeeping; it registers its own independent `listen<BatchProgressEvent>("batch:progress", ...)` (Tauri events support multiple independent listeners on the same event name) rather than routing through `batchStore` at all.

**Anti-spam granularity** (task brief + §15's own explicit "Không spam popup cho mọi event"): a job's progress ticks *within* one stage (10%, 42%, 87% while still `"Rendering"`) fire far more `batch:progress` events than there are real, meaningful steps. The store keeps a plain (non-reactive) `Map<jobId, lastStage>` and only appends a log entry the instant a job's own `stage` text actually *changes* — exactly the granularity §15's own example lines are at (one line per real step, never one line per percent). This one rule is also what makes terminal outcomes fall out for free, with no special-casing: since `process_job` already sets `stage` to `"Completed"`/`"Failed"`/`"Cancelled"` on the terminal snapshot, that's simply one more real stage-text change the exact same code path logs — `level` is derived from `job.status` (`failed` -> `error`, with `job.error` appended to the message when present; `cancelled` -> `warning`, a deliberate interruption rather than a pipeline fault; everything else, `Paused` included -> `info`).

Real, in-memory ring buffer capped at 200 entries (task brief's own suggested cap), newest-first (a log/activity feed reads top-to-bottom like a chat timeline — picked over oldest-first specifically so "what just happened" never requires scrolling down, and documented as a deliberate choice in the store's own doc comment). **Deliberately not persisted** — this is session-local activity, not a second, redundant persistence layer duplicating Phase D8a's own real `history`/`in_progress_jobs` tables, which already own the durable record of the same jobs; over-scoping this into a third persistence mechanism was considered and rejected per the task brief's own "don't over-scope this" guidance.

Exposes: `entries` (raw, newest-first), `filteredEntries` (derived off `levelFilter`), `counts` (a real `{info, warning, error}` tally over the *entire* retained buffer, not just the current filter — so a collapsed panel's header badges stay honest even while a filter is hiding most rows), `collapsed` (boolean, default `true`), `setLevelFilter`/`toggleCollapsed`/`clear`.

### 2. `components/layout/ActivityLogPanel.svelte`

## Phase D11 — Worker pool size setting (`STUDIO_PLAN.md` Phase D4a's own explicitly-flagged gap)

Closes the exact gap Phase D4a's own "Not built this pass" note named: *"no settings-persistence UI exists yet for `max_concurrent_jobs`"*. Read `batch::manager` in full (`spawn_worker_pool`, `set_worker_pool_size`, `pop_blocking`, `DEFAULT_MAX_CONCURRENT_JOBS`) before writing anything, per the task's own instruction — the rest of this section is the honesty analysis that reading produced, and what got built as a direct result of it.

### The load-bearing decision: restart-to-apply, not live-resize — and why

`spawn_worker_pool` spawns exactly `max_concurrent_jobs` real OS worker-loop threads **once**, at app startup (`lib.rs`'s `setup`). Each thread loops forever: `pop_blocking` → `run_job_with_events` → `mark_job_done` → loop. `set_worker_pool_size` today is `pub(crate)`, and only updates the `worker_pool_size` `AtomicUsize` that `WorkerPoolStatus::workers` reports — it has never actually spawned or killed a real thread.

**Growing the pool live would have been safe and easy**: spawning N additional threads that call the exact same `pop_blocking`/`run_job_with_events`/`mark_job_done` loop `spawn_worker_pool` already spawns, any time after startup, is not materially different from what already happens once at startup — `pop_blocking`'s condvar loop is already designed for an arbitrary number of concurrent callers.

**Shrinking the pool live is the real problem, and it's not a small one.** `pop_blocking`'s only cooperative-shutdown signal is `BatchJobManager::shutdown` — a single, global `AtomicBool` (`#[cfg(test)]`-only in production) that every parked worker checks every 200ms via its `wait_timeout` loop. Setting it stops **every** worker at once; there is no existing mechanism to signal "exactly N of the currently-running M threads should exit after their current job, the rest keep going." Building one — a per-worker target/generation counter, a way for a specific thread (not just "some thread") to notice it's now surplus and exit cleanly after finishing whatever job it's mid-processing, without racing `active_workers`/`worker_pool_size`'s own bookkeeping — is a real, non-trivial change to `pop_blocking`'s own condvar loop. The task brief explicitly forbade touching `pop_blocking`'s core queue/condvar logic (or `run_pipeline`) "regardless of which approach you choose" — and for good reason: this is Phase D4a's freshly-built, heavily-tested (1113 passing lib tests, including two dedicated real-concurrency tests using real `ps`-sampled ffmpeg process counts) critical-path subsystem. A half-fix that only works in the "grow" direction — live-apply when increasing, silently do-nothing-until-restart when decreasing — would be worse than no live-resize at all: it would train users to expect immediate effect, then quietly betray that expectation the first time they lower the value, which is exactly the kind of "looks like it works but doesn't, some of the time" dishonesty this codebase's discipline exists to prevent.

**Decision: `max_concurrent_jobs` is a real, honest restart-to-apply setting.** `set_max_concurrent_jobs` validates and persists a new value but never touches the running `BatchJobManager`'s pool; the value only takes effect the next time the app starts, when `lib.rs`'s `setup` hook reads it instead of always using `DEFAULT_MAX_CONCURRENT_JOBS`. This is a real, established pattern (the task brief's own framing) many apps use for exactly this kind of setting — and it's the honest choice here specifically because the alternative (asymmetric live-resize) would be less honest than no live-resize, not more.

### What was built

**Persistence layer** — new `src-tauri/src/batch/settings.rs`, following this codebase's own "app-level setting" precedent search to its actual conclusion: `stores/aiSettings.svelte.ts`/`stores/capcut.svelte.ts`/`stores/updateSettings.svelte.ts` each document that *every other* app-level setting in this app is `localStorage`-only, because no backend settings-persistence surface exists yet. That precedent could not be followed here for a real architectural reason, not a stylistic one: `spawn_worker_pool` runs inside `lib.rs`'s `setup` hook, before the webview/frontend has loaded — a value living only in the browser's `localStorage` would not exist yet at the exact moment Rust needs it. So this is the one setting in this app that genuinely needs real backend-side storage, and it uses this codebase's own established on-disk-state convention for that (`automation::io`/`templates::io`/`assets::io`'s atomic write-via-temp-file-then-`fsync`-then-rename), just for a single whole-file scalar (`$APPLOCALDATA/batch_settings.json`, `{ "max_concurrent_jobs": <usize> }`) rather than a one-file-per-item collection. `load_max_concurrent_jobs` is deliberately best-effort (missing file/corrupt JSON/out-of-range stored value all fall back to `DEFAULT_MAX_CONCURRENT_JOBS`, matching `automation::io::list_rules`'s own "absence means empty/default, not an error" convention); `save_max_concurrent_jobs` is the opposite — a real validation or I/O failure is returned to the caller, never swallowed, since silently discarding an explicit settings change would be exactly the dishonesty this codebase forbids. Bounds: `MIN_MAX_CONCURRENT_JOBS = 1`, `MAX_MAX_CONCURRENT_JOBS = 16` (real CPU-core-count territory, not "unlimited" — this app really does spawn that many real OS threads for it).

**`BatchError` gained 3 variants** (`InvalidMaxConcurrentJobs`/`SettingsStorageUnavailable`/`SettingsIoFailed`), each mapped to a stable `AppErrorPayload` code, extending the existing `every_variant_maps_to_a_stable_code` test.

**Two new Tauri commands** (`commands::batch`, thin wrappers per master prompt §66 — all real logic stays in `batch::settings`): `get_max_concurrent_jobs()` and `set_max_concurrent_jobs(value)`, both returning a real `MaxConcurrentJobsSetting { persisted, active, min, max }` — `persisted` is what's on disk (what the *next* restart will use), `active` is `BatchJobManager::worker_pool_status().workers` (what the *currently-running* pool actually has), and `min`/`max` are the real enforced bounds. ## Phase D12 — Subtitle Translation Accept/Apply UI (closes Phase S6's own "not yet built" frontend gap)

The real frontend half of Phase S6's `ai::translate_captions`: a genuine "propose -> per-caption review -> accept/reject -> apply" flow, matching this codebase's own established AI-feature discipline (`ai::edit_plan`/`ai::smart_edit`'s "propose, never auto-apply" module doc comments) instead of the session-only, no-review preview `WorkspaceSimple.svelte` had before this pass.

### What was actually there before this pass (confirmed by reading, not assumed)

`WorkspaceSimple.svelte` already tracked `translating`/`translateError`/a `translations: Record<caption_id, text>` map, wired to `PipelineStepper.svelte`'s "Translate" step — but the "Translate" button in `ScriptEditor.svelte` called `translate_captions` **directly**, with no settings beyond a bare target-language string, no source-language control, and — the real gap — **no review UI at all**: a successful call just populated the Translation column in the read-only script table. There was no way to accept, reject, or apply anything; the AI's proposed text never reached `project.captions`, so it never affected a render. This matches Phase S6's own honest "not yet built" note precisely. There was also **no backend command to write translated text back into a caption at all** — `commands::captions` had generation/split/merge/retime/find-replace/bulk-style, but nothing that could set an individual caption's `text` from an accepted AI proposal. Building the real "Accept and Apply" step therefore required one new, small, real backend command, not just frontend wiring — confirmed necessary by reading every existing caption command before concluding this, not assumed up front.

### Backend: the missing "Accept and Apply" write-back (the one new `src-tauri/` command this pass needed)

- **`timeline::captions::apply_caption_translations(project, translations: &[ai::translate::TranslatedCaption]) -> Result<Command, TimelineError>`** (new, `src-tauri/src/timeline/captions.rs`): a pure builder over `&ProjectV1`, exactly the same shape as this file's own `bulk_set_caption_style`/`find_replace_captions` — reused `ai::translate::TranslatedCaption` (`caption_id`/`translated_text`) directly as the input type rather than inventing a parallel schema, since it already carries exactly what this operation needs and is already validated by `ai::translate::parse_and_validate` on the propose side. Every real `caption_id` must exist in `project` (`TimelineError::CaptionNotFound` otherwise — the caller is responsible for only ever passing ids it actually asked to have translated, the same contract `parse_and_validate` already established). A caption whose text already exactly matches the proposed translation produces no command (same no-op-skip precedent as `bulk_set_caption_style`). `words` is unconditionally cleared — a translation always changes the caption's language, so old per-word timestamps are meaningless for the new text (an unconditional version of `find_replace_captions`'s own "changed word count drops word timing" policy, made unconditional here since translation is never a same-language, word-count-preserving edit). Produces a `Command::Batch` of `SetCaption` — the same undo-history path every other caption correction command already uses, so accepting translations is a single, real, undoable step.
- **`commands::captions::apply_caption_translations(state, translations: Vec<TranslatedCaption>) -> Result<ProjectV1, AppErrorPayload>`** (new): the thin Tauri command, registered in `specta_builder()`. This is the **only** place in the crate a translation proposal ever becomes a real project mutation — `ai::translate::translate_captions` (Phase S6) is untouched and still never mutates anything, exactly as its own module doc comment requires.
- **5 new tests** in `timeline::captions::tests`: updates text and clears word timing; only touches accepted ids (an unaccepted sibling caption is left completely untouched, confirmed by asserting its `words` too); rejects an unknown caption id; skips a no-op (identical text) entry; and a full undo/redo round trip through a real `TimelineSession`.

## Phase D14 — Recent Projects (`STUDIO_PLAN.md` audit: "Recent projects — no list/store/command anywhere")

### The real gap turned out to be one layer deeper than the audit's own note

Before writing a single line of frontend code, this pass read the real project-open/create/save flow per the task brief — `src-tauri/src/project/` (`io.rs`/`types.rs`/`error.rs`), `src-tauri/src/commands/project.rs`, and every frontend call site (`stores/timeline.svelte.ts`, `TopBar.svelte`). What that reading found: this codebase had **no real file-backed project open or save at all**. `commands::project::new_project` only ever constructs a brand-new, in-memory `ProjectV1` with no path (its own doc comment says exactly this: "Deliberately does not touch the filesystem... wiring this into a real Project Manager UI (recent projects, save/open, `project.json` on disk) is later-phase work"). `project::io::ProjectV1::save_atomic`/`load` are real, fully-tested atomic-write/load primitives (`project::io`'s own round-trip/Unicode/long-path/UNC-shaped-path test suite), but were never wired to a Tauri command or called from any frontend code anywhere — confirmed via grep across both `src-tauri/src/commands/` and `src/stores/` before concluding this, not assumed. `commands::diagnostics::SystemInformation::project_directory`'s own doc comment independently confirms the same thing: "no default project folder / recent-projects concept exists anywhere on the backend."

A "Recent Projects" list needs a real file path to be honest — this app's `new_project` button has never produced one. Fabricating a path, or building a list keyed on the in-memory-only `new_project` moment, would have violated this codebase's own "never fake a feature" discipline the task brief itself invoked. So this pass's real, necessary, and deliberately minimal first step was building the missing prerequisite: two thin Tauri commands wiring the already-tested `save_atomic`/`load` primitives to real IPC, giving this app its first-ever real "Save Project As…"/"Open Project…". Recent Projects is built directly on top of that real flow — every entry it ever shows came from an actual, successful round trip through one of these two commands.

### Backend: `save_project_as`/`open_project` (`src-tauri/src/commands/project.rs`)

- **`save_project_as(project: ProjectV1, path: String) -> Result<(), AppErrorPayload>`**: thin wrapper over `ProjectV1::save_atomic`. **`open_project(path: String) -> Result<ProjectV1, AppErrorPayload>`**: thin wrapper over `ProjectV1::load`. ### How the plugin actually persists state (confirmed by reading its real upstream source, not assumed)

Save happens in exactly two places, both already built into the plugin itself — no code at this app's own call site does anything beyond the one `.plugin(...)` registration: (1) on the window's `CloseRequested` event, it updates its in-memory per-window cache from the window's current geometry; (2) on the app's `RunEvent::Exit`, it writes that cache to `<app config dir>/.window-state.json` (confirmed on this machine at `%APPDATA%\dev.aivideoedit.app\.window-state.json`). There is no periodic/debounced save on every resize/move — only those two hooks. This means a force-killed process (crash, `taskkill /F`, task-manager "End task") loses whatever changed since the last clean close, same caveat this codebase's own `crate::logging::mark_clean_exit` already documents for its unrelated unclean-exit marker — not a new risk this phase introduces, just worth naming since it's the same shape of caveat.

### An honest, unresolved anomaly found during this testing — flagged rather than hidden

While chasing the same verification for **height**, this pass hit a reproducible oddity worth naming rather than glossing over: closing the app immediately after an untouched, default launch persists a clean `"width": 1440, "height": 900` (exactly `tauri.conf.json`'s configured default — correct). This pass could not fully root-cause it in the time available — the leading theory is a DPI/physical-vs-logical-size conversion edge case specific to a raw `SetWindowPos` call (as opposed to the OS's normal interactive live-resize loop a real user's mouse-drag goes through), possibly in the `tao`/`wry` windowing layer under this machine's window, not something introduced by `tauri-plugin-window-state` itself (the plugin only ever reports/persists whatever size the window layer tells it). **This pass deliberately did not attempt to simulate a real mouse-drag resize to rule this out**: the test machine's screen was a live, shared remote-desktop session with the human's own active work visibly on screen (other windows, chat panes, editors), and a coordinate-targeted synthetic mouse-drag risks mis-clicking into the wrong window if the target corner estimate is even slightly off — an unacceptable risk to take against someone else's live session for a verification step.
