## What this project is

Building "AI Video Editor": a Windows 10/11 x64 desktop app (Tauri 2 + Rust + Svelte 5) that unifies two open-source repos into one coherent product — silence/speech auto-cutting, CapCut/Jianying draft export, transcription, AI semantic editing, captions, shorts generation, etc.

**The spec is** `MASTER PROMPT — BUILD AI VIDEO EDITOR FOR WINDOWS.md` at the repo root — 90 sections, read it, it is the actual product requirements, not a summary of them. It explicitly instructs: audit first, then implement phase by phase, compiling/testing/committing at the end of each phase, never faking a feature or claiming something works when it wasn't verified (§75, §90-93).

## Decisions already made — don't re-litigate these

1. **Timebase: `i64` microseconds**, everywhere in the core model. Conversions to FFmpeg (seconds) and FCPXML (rational frames) happen only at those adapters' boundaries. See `docs/architecture.md`'s "Timebase conversion boundaries" table.
2. **autocut code may be copied/ported directly, not just referenced.** The project owner (via chat, not a written grant on file) said permission was obtained from the autocut author, Mert Cobanov, despite the upstream repo carrying no LICENSE file. This is recorded in `docs/upstream.md` and `THIRD_PARTY_NOTICES.md`. If this ever needs to hold up to outside scrutiny, get the grant in writing and link it from those two files — right now it's a verbal/chat-relayed permission, not a documented one.
3. **capcut-mate's draft engine (`pyJianYingDraft`) is a direct Rust port**, Apache-2.0, no licensing concern. Its FastAPI/HTTP/cloud-storage/RPA-rendering layers are explicitly NOT ported (this app is local-only, no HTTP server, no Docker).
4. **No Python runtime shipped.** Everything reusable from capcut-mate is ported to Rust, not run via a Python sidecar.
5. **Bundle identifier**: `dev.aivideoedit.app`.
6. **Windows ffmpeg/ffprobe binary sourcing — resolved in Phase 12** (was previously deferred here, master prompt §59): BtbN/FFmpeg-Builds, tag `autobuild-2026-09-05-13-10`, static **GPL** Windows x64 build of **FFmpeg 9.0.1** (GPL, not LGPL, deliberately — see `THIRD_PARTY_NOTICES.md`'s "FFmpeg / FFprobe" section for the full reasoning). `scripts/fetch-ffmpeg.ps1` fetches+checksum-verifies it into `src-tauri/binaries/` — **run once by a human on Windows before a real `tauri build`/`tauri dev` needs the sidecar**; not yet run by any agent session (needs real Windows + network access). Dev/test work in WSL2/CI still uses the Linux build server's apt-installed `ffmpeg`/`ffprobe` via a PATH fallback (`ffmpeg::binaries`'s dev/test-only fallback) — that remains correct and is NOT the shipping decision, which is the paragraph above.
7. **CapCut/Jianying automated rendering via RPA** (capcut-mate's `jianying_controller.py` approach) is deferred to P2-or-later, optional/experimental only — never the primary render path. Local FFmpeg rendering (Phase 6) is the default, always-available path.

**Update, 2026-09-05: native `cargo build`/`test`/`clippy` on this Windows machine is BLOCKED — Windows Smart App Control silently flipped from Evaluation to enforced "On" partway through Phase 6** (confirmed via `Get-MpComputerStatus`'s `SmartAppControlState: On` and `HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy`'s `VerifiedAndReputablePolicyState: 1`), which blocks execution of any unsigned/freshly-built binary — `cargo build` itself fails because even its own build-script executables get blocked (`An Application Control policy has blocked this file`, os error 4551). **Per Microsoft's own documentation this can only be turned back off by a clean Windows reinstall/reset — there is no Settings toggle once it's "On".** Do not attempt to "fix" this; it's a user-only decision. **Current working local setup: WSL2 + an imported Ubuntu 24.04 distro named `Ubuntu-CapCut`**, which fully bypasses the problem (Smart App Control only polices Windows PE executables; Linux ELF binaries running under WSL's own kernel aren't in its scope). How this was set up, in case it needs to be redone on another machine:
- WSL2 itself needed `wsl --install` (as admin) + **a reboot** to actually enable the underlying `VirtualMachinePlatform`/WSL Windows features (the first attempt silently no-opped until after reboot).
- The distro was NOT installed via the normal `wsl --install -d Ubuntu` interactive flow — that hangs forever in a non-interactive/background shell waiting for a username/password prompt on a console handle piped input can't reach. Instead: downloaded Canonical's official prebuilt WSL rootfs directly (`https://cloud-images.ubuntu.com/wsl/releases/24.04/current/ubuntu-noble-wsl-amd64-24.04lts.rootfs.tar.gz`, ~340MB) and ran `wsl --import` — fully non-interactive, logs in as `root` by default, no OOBE prompt at all.
- Inside the distro (`wsl.exe -d Ubuntu-CapCut -u root -- bash -c "..."`): `apt-get install` for `build-essential curl git pkg-config libssl-dev libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libayatana-appindicator3-dev libsoup-3.0-dev ffmpeg espeak-ng`, then `rustup` (`curl https://sh.rustup.rs | sh -s -- -y`) and Node LTS via `deb.nodesource.com`'s setup script.
- **The distro's vhdx lives at `D:\WSL\Ubuntu-CapCut\ext4.vhdx` — NOT on `C:`.** It was originally imported to `C:\Users\<user>\WSL\Ubuntu-CapCut` and grew to ~16GB after compiling `whisper-rs`/whisper.cpp (Phase 7), which — combined with this machine's `C:` drive already being nearly full from unrelated things (browser profile, games, VS Build Tools, etc.) — filled `C:` to **0 bytes free** mid-session and crashed WSL outright (`Wsl/Service/E_UNEXPECTED`, "Catastrophic failure"). Fixed by: `wsl --shutdown`, freeing a couple GB on `C:` (this session deleted its own now-useless `C:\Users\<user>\.rustup`/`.cargo` — the native Windows Rust toolchain from before Smart App Control blocked it, ~1.86GB, **with explicit user permission first**, since deleting things under a user's home directory is exactly the kind of action to confirm rather than assume), then `wsl --export Ubuntu-CapCut D:\<tar path>` → `wsl --unregister Ubuntu-CapCut` (reclaims the old `C:`-based vhdx entirely) → `wsl --import Ubuntu-CapCut D:\WSL\Ubuntu-CapCut D:\<tar path> --version 2`. **If setting this up fresh on another machine, import directly to a `D:`-or-similar-large-drive path from the start** — don't repeat the mistake of defaulting to `C:\Users\<user>\WSL\...`. `diskpart`'s `compact vdisk` (attach readonly → compact → detach) reclaims disk space from a vhdx that has genuinely freed internal blocks, but only after the guest OS has actually deleted the corresponding files — it did almost nothing here (91MB) because the 16GB was real, still-live build-cache data, not slack; moving the whole distro was the only real fix once `C:` itself had no room left to grow into.
- **Always set `export CARGO_TARGET_DIR=$HOME/capcut-target-linux`** (or similar, inside the Linux home directory, NOT under `/mnt/d/...`) before any `cargo` command run from WSL against this shared repo checkout. The repo itself is accessed in-place at `/mnt/d/Work/Work-out/capcut-auto` (the same Windows checkout, via the 9p mount) so uncommitted work is never duplicated/lost, but Cargo's own `target/` build-artifact directory must stay separate from Windows' `target/` (different object-file formats: ELF vs PE) — sharing one `target/` between a WSL cargo run and a Windows cargo run works by accident (Cargo just does a full rebuild when the fingerprint/host mismatches) but isn't worth the risk or the wasted rebuild time. Now that the vhdx itself lives on `D:` with hundreds of GB free, this directory has plenty of headroom for even large native-dependency crates (whisper.cpp, etc.).
- **Never run `pnpm`/`npm` from inside WSL against this shared repo's `node_modules/`.** This was tried once and it corrupted `node_modules/.bin` (platform-specific native binaries like `esbuild` got swapped/removed), breaking `pnpm run build`/`check` back on the Windows side until `Remove-Item -Recurse -Force node_modules` + a clean `pnpm install` from Windows PowerShell fixed it. WSL is for `cargo`/Rust work ONLY; all frontend/pnpm work stays on the Windows side (unaffected by Smart App Control — Node isn't blocked, only compiled Windows executables are).
- Net effect: `cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` / `cargo test --lib` / `cargo run --bin export_bindings` all run from WSL exactly as they did natively on Windows before the lock — same 228+ passing tests (Linux is just another supported host triple for this project, nothing in the Rust code is Windows-only).
